# Decision Log (08_DECISION_LOG.md)

This log tracks architectural and product decisions, open questions, and recommended paths.

## These entries are living records, not constraints

An entry records the best decision available when it was written, together with
the evidence behind it. When later measurement or a later product decision
contradicts one, **amend the entry** -- add an `Amended` block stating what
changed, when, and on what evidence, and update `Status` to `Superseded` if the
original decision no longer holds at all. Do not bend an implementation to
preserve a stale entry, and do not silently diverge from one either: an entry
that no longer matches the code is worse than no entry, because it is read as
current.

The evidence in a superseded entry stays valuable -- it records what was tried
and what it measured -- so entries are amended in place rather than deleted.

### DEC-013: Landmark-Assisted Geometric Head-Box Estimation Baseline Selection
- **Date**: 2026-06-17
- **Status**: Approved
- **Problem**: Selection of a local CPU-compatible baseline approach for provisional head-region estimation.
- **Options Considered**:
  - Option A: Landmark-Assisted Geometric Heuristic Expansion. Pros: 0 MB size, < 0.1 ms latency, 100% deterministic, no external dependencies, high privacy. Cons: Heuristic vertical/horizontal bounds (cannot observe actual hairline or chin boundaries).

- **Reasoning**: It is extremely fast, lightweight, introduces no new runtime dependencies, and is fully deterministic, providing a safe fallback crop frame.
- **Consequences**: Boundary visibility states remain "unknown" or "geometry_inferred" / "landmark_inferred" (cannot report "observed"). Clamping to image bounds reports clipping as "suspected" instead of "confirmed".

### DEC-025: Generalized Adaptive Portrait Composition and Edge-Matting Hardening
- **Date**: 2026-06-22
- **Status**: Approved
- **Problem**: Hardening the image compliance engine to produce high-quality, compliant portrait crops and composites across diverse human subjects without overfitting, clipping hair/ears, or introducing grey/white edge halos and color spill.
- **Decision**: Adopt the following comprehensive visual quality and adaptive composition enhancements:
  - **Composition 1.1 Model**: Introduce CropProfile and EarsPolicy schemas with validators mapping default ratio constraints (head size, margins, eye-line, torso limits) dynamically.
  - **Fused Head Refinement**: Implement a post-segmentation fused head refinement using an adaptive head ROI to accurately locate the hair/chin boundary, ignoring the torso.
  - **Grid-Search Cost Minimization**: Generate candidate crops and select the lowest cost crop using multi-objective scoring.
  - **Guided Filter Matting**: Compute a trimap and uncertainty band at reduced resolution, project to native resolution, and refine the alpha mask using Guided Filter on the RGB guidance image.
  - **Edge Color Decontamination**: Restrict background color spill recovery strictly to the boundary region ($0.05 < \alpha < 0.95$) to prevent global biometric color shifts.
  - **Premultiplied Compositing**: Crop, premultiply, resize RGB/alpha together, and composite on white target background to prevent dark/bright edge fringes.
  - **Comprehensive 30-Subject Benchmark**: Freeze baseline metrics (IoU, halo, spill, continuity, uniformity) and enforce visual quality gates on 192 deterministic variants.
- **Reasoning**: Ensures robust, generalized compliance outputs for diverse skin tones, hairstyles, facial hair, clothing, and headwear, while satisfying strict privacy-first constraints and preserving subject identity.
- **Affected Modules**: `services/image-engine/providers/refiners`, `services/image-engine/providers/crop_planners`, `services/image-engine/providers/background_composers`, `services/image-engine/providers/premultiplied_compositing.py`, `services/image-engine/providers/foreground_decontamination.py`, `services/image-engine/providers/fused_head_refinement.py`, `scripts/benchmark_engine_quality.py`.
- **Approval Owner**: Lead Architect

### DEC-026: Preservation-First Arbitrary Source Framing
- **Date**: 2026-07-06
- **Status**: Approved
- **Problem**: Candidate uploads can use arbitrary source dimensions and loose selfie framing, while exam outputs still require exact or rule-selected dimensions, clean white background replacement, target file size, and safe filenames without cutting hair, ears, chin, or beard boundaries.
- **Options Considered**:
  - Reject sources when a tight exact-aspect crop would extend beyond source pixels.
  - Preserve the subject by allowing transparent out-of-source crop regions that become the configured solid background during final composition.
- **Decision**: Use preservation-first framing. Crop Mode A remains selected for exact dimensions, Crop Mode B remains selected for ranges or unspecified dimensions, and rule face-coverage percentages map to target/min/max head-height crop ratios. Rule-orchestrated processing may use background-colour padding to satisfy exact output frames while keeping subject clipping disabled by default.
- **Reasoning**: This matches real candidate-upload behavior and prevents false "not possible" failures when a compliant result can be produced by tight subject framing plus white background composition.
- **Consequences**: Outputs can include white padding outside the original source bounds, but not stretched pixels or clipped subject features. Rules with unspecified dimensions use the documented platform default profile dimensions before compression.
- **Affected Modules**: `services/image-engine/src/exam_photo/orchestration`, `services/image-engine/src/exam_photo/providers/crop_planners`.
- **Approval Owner**: Lead Architect

### DEC-027: Semantic Exam Portrait Composition Boundary
- **Date**: 2026-07-06
- **Status**: Approved
- **Problem**: A single head/foreground geometry was being used for multiple concerns: background removal, head preservation, crop sizing, and torso inclusion. Full-person segmentation can include neck, collar, shoulders, and torso; when that geometry influences crop sizing, tight exam outputs become too loose and face coverage drops even when the face and head were detected correctly.
- **Options Considered**:
  - Tune crop thresholds for individual failing photos.
  - Continue using the refined foreground mask as the crop-preservation source.
  - Add a semantic exam-portrait composition stage between head refinement and crop planning.
- **Decision**: Adopt a semantic `PortraitCompositionResult` produced by `DeterministicPortraitCompositionEstimator`. Crop Mode A and Crop Mode B must use the portrait preservation/framing box for crop geometry and preservation validation. The refined alpha mask remains available for background removal and secondary mask checks, but full foreground bounds must not drive tight crop sizing.
- **Reasoning**: This fixes the engine contract rather than a single output. It generalizes across loose selfies, different source dimensions, hairstyles, beards, collars, and shoulder-heavy foreground masks while preserving the subject identity and preventing hair/ear/chin/beard clipping.
- **Consequences**: Pipeline reports now expose `portrait_composition_box` and lower-body exclusion geometry for debugging. If composition estimation fails, the pipeline falls back to head geometry with a warning, never to full foreground-driven crop geometry.
- **Affected Modules**: `services/image-engine/src/exam_photo/providers/portrait_composition.py`, `services/image-engine/src/exam_photo/providers/crop_planners`, `services/image-engine/src/exam_photo/orchestration/rule_pipeline.py`, `services/image-engine/tests/providers/test_portrait_composition.py`.

### DEC-029: Anatomical Head Span as the Composition Reference
- **Date**: 2026-07-31
- **Status**: Approved
- **Problem**: Measured against a 60-photo reference set (six exact-dimension exam size classes, 10 photos each), engine output was systematically under-cropped: head height 0.60 of frame versus 0.84 in the reference, headroom 0.125 versus 0.048, side space ~2.7x too wide, and face area roughly half. Only 30/60 reference inputs produced any output at all. Two root causes were isolated. First, DEC-026 mapped `face_coverage_*` percentages onto `*_head_height_ratio`; these are different quantities (a correctly composed reference photo measures 0.84 head height but only 0.29 face area and 0.58 face height), and the mapping additionally turned a diagnostic into a hard reject bound, contrary to the AGENTS.md principle that face coverage is "a diagnostic indicator, not a rigid mathematical rejection threshold". Second, DEC-027's preservation box was used as the composition reference, but it deliberately extends past the head (measured 1.140 +/- 0.011 times the crown-to-chin span, and 1.31 times the head width) because it absorbs hair spread, shoulder alpha and a lower-body exclusion band. Enforcing "head height = 0.77" against that inflated box yields a real head height of 0.665, and reaching 0.84 would require a ratio above 1.0, which is unreachable. Requiring the crop to contain the full preservation box width additionally capped achievable head height below the allowed minimum for 23/50 photos, concentrated in tall target aspects (7/8 in the 1200x1800 class).
- **Options Considered**:
  - Raise the configured ratios in preservation-box space. Rejected: the required target exceeds 1.0 for the vertical case, and the horizontal inflation factor is far less stable (sd 0.166) than the vertical one (sd 0.011).
  - Tune per-size-class constants. Rejected as fixture-fitting; it does not correct the underlying unit mismatch.
  - Separate the two roles the single box was serving.
- **Decision**: Split the geometry into a *generous* preservation box (unchanged, used to avoid cutting into the subject casually) and a *mandatory* region — crown to chin-plus-beard-margin, spanning the head core — against which composition ratios, planning constraints and preservation validation are all stated, so the planner cannot produce a crop its own validator then rejects. The crown is read from the observed subject mask rather than the geometric `face_top - 0.6 * face_height` estimate, which overshoots badly when the detector returns an oversized face box. `face_coverage_*` no longer contributes to head-height geometry and remains a reported diagnostic. `TIGHT_EXAM_PORTRAIT` profile ratios, side/bottom margins, mask-preservation threshold and preferred face-centre are recalibrated to the reference distribution. Whether outer hair is given up is decided per photo, not by a profile label: the candidate search scores both a strict variant (keeps the entire preservation box) and a relaxed one (keeps the head core plus the chin/beard margin), and a strict crop always wins when the photo admits one, so no subject area is sacrificed unnecessarily. Only subjects that cannot be composed strictly - voluminous hair, tall target aspects, a head near the source edge - fall back to the relaxed result, which is what reference photos do for those same subjects (the head silhouette touches the left edge in 31/60 and the right edge in 44/60). Preservation validation, reported margins and the mask-retention metric are all judged against whichever region that photo's crop actually promised, and the mask-retention metric is measured over that region rather than a fixed expansion beyond it. The legacy (no-profile) planning branch keeps its original "crop contains the preservation box" contract unchanged.
- **Reasoning**: The reference set shows very low variance in the landmark-derived quantities (eye line 0.486 +/- 0.033, chin 0.888 +/- 0.043, head height 0.840 +/- 0.056), so these are stable engine targets rather than per-photo preferences. Fixing the reference frame corrects the contract instead of compensating for it downstream.
- **Consequences**: Over the 60-photo reference set, pipeline success rose from 30/60 to 56/60 and head height from 0.600 to 0.753 mean / 0.804 median against a 0.840 target, with every measured composition metric moving closer to the reference. Head-height error fell from 0.240 to 0.087 and head-width error from 0.236 to 0.050. Crop-stage validity is 58/58 of photos that reach planning, with head coverage of the mandatory region at exactly 1.000. Face detection gained a confidence-recovery ladder because the short-range BlazeFace model returned no detections at all on 9/60 ordinary half-body submissions; recovery accepts only an unambiguous single face, so genuine multi-person photos still fail. The `full_range` model remains unusable here (the manifest records it as incompatible with the Python Tasks FaceDetector API). The mask-retention metric previously sampled a region 35% wider and taller than anything the planner guaranteed, so a correctly composed crop could fail a bar nothing targeted; aligning it to the guaranteed region fixed both this and a pre-existing CLI test failure. The `case_marie_curie` golden baseline was regenerated because it encoded the old composition; the new output is visually a tighter, better-framed crop. Full suite: 253 passed, 0 failed, with ruff/format/mypy clean. Residual gap: 8 photos remain under-cropped because segmentation retains background objects adjacent to the subject (signboards, gates, wall panels), which inflates the observed subject extent; mask validation and matte validation both pass these, so the blind spot is logged as follow-up work rather than resolved here.
- **Affected Modules**: `services/image-engine/src/exam_photo/providers/crop_planners/deterministic_crop_planner.py`, `services/image-engine/src/exam_photo/orchestration/rule_resolver.py`, `services/image-engine/src/exam_photo/orchestration/rule_pipeline.py`.

### DEC-030: Matte Resolution, Band Width and Alpha Contrast Window
- **Date**: 2026-07-31
- **Status**: Approved
- **Problem**: Edge quality was limited by the refinement stage discarding detail the segmenter had already produced. Measured on a reference photo, the raw segmentation probability mask carried genuine partial coverage over 4.64% of the frame; after refinement only 1.22% survived. Three independent causes: (a) `maximum_matting_pixels` (2 MP) demoted an ordinary 10.6 MP phone photo a whole quality tier, pinning matting to a 1024px working resolution; (b) the "unknown" band the guided filter is allowed to write into was computed at a fixed 512px and upsampled with NEAREST, so it arrived quantised into ~8px blocks and the filter could only ever produce a blocky edge regardless of its own resolution; (c) the alpha contrast window (0.18/0.72 followed by a smoothstep) clipped 46% of the alpha range, which is precisely the range that describes hair.
- **Options Considered**:
  - Raise the memory budget. Rejected: peak memory is a real constraint and the budget was not the problem, the policy for spending it was.
  - Widen the matting band aggressively. Measured and rejected: at 0.025 of head height the band exceeded the reach of colour decontamination, so its interior kept background colour; hair detail rose but the halo proxy more than doubled.
  - Replace the segmenter with a portrait matting model. Deferred; see Consequences.
- **Decision**: Derive the working resolution by scaling to the pixel budget instead of dropping a quality tier, keeping ~1.7x the linear resolution at identical peak memory. Build the matting band at the refinement resolution from a smoothly resampled decision rather than a NEAREST-upsampled 512px one. Size the band from estimated head height rather than a fixed pixel count, bounded so it stays within the colour-decontamination reach, and raise that reach to match. Widen the alpha contrast window to 0.05/0.92. Morphology at the refinement resolution uses Pillow's C rank filters applied iteratively, which is linear in radius and adds no dependency beyond Pillow and numpy (OpenCV is only present transitively via the optional `face` extra and must not become a core requirement).
- **Reasoning**: Each cause was isolated by measurement rather than tuned together: retained soft alpha moved 1.22% -> 1.46% (resolution) -> 2.29% (contrast window) -> 3.08% (band width) against a 4.64% ceiling. Re-running with the contrast window reverted showed the halo proxy stayed elevated, which reattributed that cost to the resolution and band work rather than to the window.
- **Consequences**: Over the 60-photo reference set, hard-edge fraction fell from 0.390 to 0.300 (reference photos measure 0.567, so engine output is now materially softer and more natural than the references it was calibrated against, which is the intended direction). Composition is unaffected. The `halo_score` proxy rose from 0.756 to 1.121, but direct pixel inspection shows finer individual hair strands and no grey ring, and background purity is essentially unchanged (`bg_pure_white_frac` 0.868 -> 0.862), so the proxy is partly conflating additional genuine soft-edge detail with contamination; it should not be optimised against on its own. The `case_marie_curie` golden baseline was regenerated (MAE 8.59, matte-only, composition unchanged) and shows visibly finer strand detail. Full suite: 253 passed, 0 failed, ruff/format/mypy clean. This is the limit of what the current selfie segmentation model supports; per-strand hair requires a real portrait matting model (BiRefNet MIT or BEN2 Apache-2.0 via onnxruntime; RMBG-1.4 is non-commercial and unsuitable), which remains the outstanding step change.
- **Affected Modules**: `services/image-engine/src/exam_photo/providers/refiners/morphological_refiner.py`, `services/image-engine/src/exam_photo/providers/foreground_refinement.py`, `services/image-engine/src/exam_photo/providers/foreground_decontamination.py`, `tests/golden-images/case_marie_curie.golden.jpg`.
- **Approval Owner**: Lead Architect

### DEC-031: BiRefNet Subject Matting Backend
- **Date**: 2026-08-01
- **Status**: Approved
- **Problem**: Reviewer assessment of engine output was that roughly 95% of results were unusable, with two specific complaints: a hard line visible around the face/jaw, and crops that were too loose. Inspection of the alpha mask showed the cause was not tuning but the segmentation model itself: MediaPipe selfie segmentation produces a "sticker" matte (flat alpha 1.0 across the subject, hard boundary, faceted straight-line shoulders, transparent holes inside the face box), and absorbs background structures adjacent to the subject (signboards, gates, wall panels) into the subject mask. DEC-030 had already extracted essentially all detail that model produces (3.08% soft alpha against its own 4.64% ceiling), so no further tuning was available.
- **Options Considered**:
  - RMBG-2.0. Rejected: BRIA's model card records it as "developed on the BiRefNet architecture" -- the repository ships `birefnet.py` and `BiRefNet_config.py` -- so it is the same design under CC BY-NC 4.0, gated behind licence acceptance, and it scored *lower* than permissive BiRefNet on 5 of 6 measured images while being visually indistinguishable. Adopting it would cost monetisation rights for no measured gain; BRIA sells a commercial agreement if it is ever wanted.
  - BEN2 (Apache-2.0). Rejected on measurement: lowest edge-alignment score of the four backends (4.04) and slowest (120-167 ms/image at its fixed 1024 input, which its ONNX graph cannot vary), plus one hard failure.
  - Continue tuning MediaPipe. Rejected as exhausted per DEC-030.
- **Decision**: Adopt BiRefNet (MIT) as an opt-in subject segmentation backend at 512px inference, selected via `RuleOrchestratedPipeline(matting_backend="birefnet")` or CLI `--matting-backend birefnet`. The default remains `"mediapipe"` so existing callers, tests and deployments are unchanged. Weights are vendored to `model-assets/birefnet/` by `scripts/download_birefnet.py`, pinned to revision `e2bf8e44` and SHA-256 verified against `model-manifests/birefnet.json`, matching the existing face-detector and segmenter model handling. `torch`/`transformers` are an optional `matting` extra and are imported lazily so the package remains importable without them.
- **Reasoning**: Selection was made on measurement rather than reputation. A new `edge_alignment` signal (gradient magnitude along the matte boundary relative to subject interior) was introduced because three earlier candidate signals failed validation against known-good/known-bad photos -- two pointed the wrong way -- and because the reported defect is a boundary that sits off the true subject edge, which silhouette-shape metrics cannot see. Inference resolution was chosen by sweep: 512 matches 1024's edge-alignment score (4.72 vs 4.80) and is visually indistinguishable while running ~7x faster on CPU (12s vs 85s), and 384 degrades sharply.
- **Consequences**: Over the 60-photo reference set, valid outputs rose from 56/60 to 57/60 and hard-edge fraction fell from 0.390 to 0.337 (reference photos measure 0.567, so output remains materially softer than the set it is calibrated against). Background removal is qualitatively fixed: structures previously absorbed into the mask are now excluded. Composition improved only marginally (head height 0.749 -> 0.754, mean; median 0.784 against a 0.840 target, 8 photos still below 0.70) because **crop geometry is derived from the detector face box, not from the mask** -- so a better matte cannot fix it. Three latent bugs were found and fixed while integrating, all previously masked by the poor segmentation: (a) `preserve_face_core` force-filled the entire inner face-box rectangle to opaque regardless of the segmenter's output, reintroducing background the model had correctly excluded; (b) `_estimate_crown_y` rejected any mask crown reading below `face_box.top`, discarding ground truth precisely when the face box was oversized; (c) the same phantom space remained in `preserve_box`, making crop sizing reserve room for absent subject. Fix (c) initially regressed one photo by trimming `preserve_box` without trimming `composition_box`, so preservation validation judged the crop against a region the planner no longer promised -- the same planner/validator disagreement class as DEC-029, corrected by trimming both. Cost: `torch` is ~2 GB and BiRefNet runs ~12s/image on CPU versus ~4.5s for MediaPipe; the API is already job-based with polling so this is viable, and ONNX export plus int8 quantisation remain available.
- **Residual**: BlazeFace short-range returns no detection on 9/60 reference photos and a poor box on those recovered by the confidence ladder, and its eye keypoints are corrupted by sunglasses, which blocks the eye-line constraint. Since all crop geometry depends on that box, the outstanding work is to derive head geometry (crown, head width, shoulder line) from the now-accurate matte and use face landmarks only for eye line and chin. That is expected to address the ~8 still-loose photos as a class rather than individually.
- **Affected Modules**: `services/image-engine/src/exam_photo/providers/segmenters/birefnet_segmenter.py`, `orchestration/rule_pipeline.py`, `cli.py`, `providers/refiners/morphological_refiner.py`, `providers/crop_planners/deterministic_crop_planner.py`, `scripts/download_birefnet.py`, `model-manifests/birefnet.json`, `pyproject.toml`.

### DEC-033: Preserve Trusted BiRefNet Alpha
- **Date**: 2026-08-01
- **Status**: Approved
- **Problem**: Morphological reconstruction was designed for coarse MediaPipe masks. Applied to BiRefNet probability masks, it discards useful soft-edge detail and can reintroduce the hard-cutout behavior the model was selected to avoid.
- **Decision**: Add a trusted-alpha path for BiRefNet output. When the segmenter supplies a high-quality probability mask, skip destructive morphology and pass the alpha through to later composition/decontamination stages.
- **Reasoning**: The product defect is edge realism. BiRefNet already predicts soft foreground probabilities; preserving that signal is safer than forcing it through coarse-mask cleanup.
- **Consequences**: MediaPipe masks still use the existing refinement path. BiRefNet output keeps finer hair and jaw transitions, with tests covering exact alpha preservation.
- **Affected Modules**: `services/image-engine/src/exam_photo/providers/refiners/morphological_refiner.py`, `services/image-engine/tests/providers/test_foreground_refinement.py`.
- **Approval Owner**: Lead Architect
- **Amended 2026-08-06 (the trusted path skipped a correction it still needed)**: The product owner flagged delivered photographs as having "soft, smooth grey edges, looks like smudged" -- most visibly on photos 17, 18 and 19, which HANDOFF-INVARIANTS.md already tracked as M22. Diagnostic capture of the raw BiRefNet probability mask at native resolution showed why: a genuinely wide, low-texture transition band between foreground and background (roughly 1.85% of the frame in the 0.02-0.98 probability range on photo 17), which composites as a soft grey-white halo rather than a clean edge. This entry's own "skip destructive refinement" reasoning was correct about morphology and guided filtering -- both were built for MediaPipe's coarse mask and do discard genuine BiRefNet detail -- but it was applied too broadly: `alpha_snap_low_threshold`/`alpha_snap_high_threshold` (0.05/0.92, DEC-030) plus a smoothstep is not morphological reconstruction, it is a dedicated anti-halo contrast correction ("this contrast step removes the broad semi-transparent halo that creates grey outlines after compositing" -- from the code comment where it already existed for the coarse-mask path), and the trusted-alpha path bypassed it entirely along with everything else. Two other candidate causes were measured and ruled out before this one: the DEC-040 crop-region re-matte only reaches 1.7x effective resolution on photo 17 rather than DEC-040's median 2.1x, but the raw alpha at that resolution is still what shows the wide band, not a resolution shortfall specific to this photo; and a vertical striping pattern visible above the hairline on photo 17 was confirmed present, unchanged, in the untouched source photo -- genuine backlit flyaway hair, not a decontamination artifact -- after a 4-to-8-connected propagation-neighbourhood change was tried, showed no effect, and was reverted rather than kept on the strength of "seems more correct."
- **Decision**: Apply the same `snap_alpha_contrast` correction (extracted as a shared function) to the trusted-alpha path, using the same thresholds already measured for the coarse-mask path. Also apply it to the DEC-040 crop-region re-matte splice in `rule_pipeline.py`, which calls the segmenter directly and therefore never passed through `refine_mask` at all -- a second, previously unnoticed gap in the same shape, since that splice is what actually reaches the frame in the region that matters most.
- **Reasoning**: Morphological reconstruction and the contrast snap are different kinds of correction. The former reshapes the mask's geometry (erosion, hole-filling, guided filtering) using assumptions about a coarse, blocky input; discarding it for BiRefNet was correct because BiRefNet's mask does not have that shape of defect. The contrast snap does not reshape anything -- it rescales the existing probability values, so it cannot invent or remove strand-level detail; it only compresses the low-confidence middle of the range BiRefNet already produced. That makes it a fit for both segmenters despite them producing differently-shaped output, and it is why the two segmenters' thresholds are shared rather than re-derived.
- **Consequences**: Measured on photo 17 (crown region, native 1280x960 resolution): the fraction of pixels in the 0.02-0.98 probability range fell from 1.85% to 0.95% after the snap. Visually confirmed on photos 17, 18 and 19 -- the flagged set -- with the crown edge visibly crisper and the wide grey-white halo band reduced; real backlit hair-strand detail on 17 is unaffected, since the snap only compresses the already-existing low-confidence band rather than removing structure from it. Format/lint/mypy clean; fast suite 274 passed; output-invariant sweep 0/960; `mandatory_refinement` + `mandatory_engine_quality` + `mandatory_api` 14 passed; `mandatory_rule_pipeline` 30 passed. `test_trusted_alpha_skips_destructive_refinement` updated: it asserted exact pass-through of the input alpha, which the snap now deliberately changes for semi-transparent pixels; it now asserts pass-through for fully opaque/transparent regions and asserts the boundary rows equal the snap's own output, so the test stays load-bearing for what it can still guarantee -- morphology and guided filtering are skipped -- without asserting a behaviour the fix intentionally ends.

### DEC-038: Face Containment Anchored on Measured Anatomy
- **Date**: 2026-08-04
- **Status**: Approved
- **Problem**: Crop validation required the crop to contain the raw BlazeFace rectangle, while the candidate search enforced containment of the anatomical `mandatory_box` and knew nothing about that rectangle. - **Status**: Approved
- **Problem**: Reviewer assessment of output was streaked hair edges, halos and colour bleed spreading into the face and ears. The cause is resolution, not tuning. BiRefNet sees a fixed 512x512 square, so the alpha detail any part of the subject receives is set by how much of the *source frame* it occupies, not by how large it will be in the finished photo. Candidates submit half- and full-body photographs and the exam photo is a tight head crop, so the head is the small part of the input that becomes the whole output. Measured over the 60-photo set: the head arrives with a median of 121 px of alpha detail (worst 42 px) and is magnified by a median 2.1x, worst 17.4x. Every photo with visible streaking or halo sits in the high-magnification group.
- **Decision**: After crop planning, re-run the matting model on the planned crop region plus a 12% margin and splice the resulting alpha back into the full-frame mask, so decontamination and compositing both consume the sharpened matte. Skip when the region is within 1.15x of the full frame, and treat any failure as a warning that degrades edge detail rather than failing the photo. Crop geometry is already decided at that point and is not revisited, so this cannot feed back into planning.
- **Reasoning**: Spending a fixed model resolution budget on the whole frame when only the head survives is the direct cause of the defect; no tuning of band widths or decontamination reach can recover detail the model never produced. Two competing hypotheses were falsified with measurement before this one was adopted: out-of-bounds padding blanking the subject (0 of 57 outputs cut the subject at a padded band) and the crop frame clipping ears (1 of 57 touches a side edge more than its ideal does).
- **Consequences**: One extra inference per photo, roughly doubling matting cost on photos that qualify; the API is job-based so this is acceptable. Spot-checked on `6-9`, `6-5`, `6-6` and `5-2`: effective alpha resolution up 2.5-3.5x and edge quality closer to the matching ideal on 14 of 15 regional measures. It does not close the gap on the 1200x1800 class, where the limit is source resolution rather than matte resolution: that class needs a median 4.41x (worst 6.98x) enlargement of real source detail, while every other size class is downscaling. That is an input-suitability problem and is addressed separately.
- **Affected Modules**: `services/image-engine/src/exam_photo/orchestration/rule_pipeline.py`, `scripts/benchmark_reference_pairs.py`.
- **Approval Owner**: Lead Architect

### DEC-041: Accept, Warn, Block -- the Output Disposition Policy
- **Date**: 2026-08-04
- **Status**: Approved
- **Problem**: A published upload manual will tell candidates which photographs are rejected, so the engine's dispositions become public promises. The tempting reading -- enforce every published exam rule and refuse non-compliant photographs -- fails commercially and factually. Candidates come to the platform to receive a compliant photograph, not to be assessed; a refusal and a silent failure are the same outcome to them, and both lose the user. Research across 48 examinations (see DEC-042) additionally shows that three of the five most commonly published rules -- recency, live capture / own photograph, and identity match at later stages -- cannot be verified from pixels at all, and that several appearance rules are mutually contradictory between bodies.
- **Decision**: Dispositions are decided by one principle: **block only when the engine cannot produce a truthful output; otherwise always produce, and report what is risky.** This yields three buckets. (1) *Auto-fix, silent*: background, crop and face coverage, dimensions, DPI, file size, format, colour space, filename. (2) *Produce and warn*: every detectable appearance defect the engine cannot repair -- blur, non-frontal pose, closed eyes, sunglasses, cap or head covering, mask, spectacle glare, harsh shadow, hidden ears, greyscale where colour is required, source resolution insufficient for the target size. Warnings carry two severities: `likely_rejection` and `possible_issue`. (3) *Block*: only an undecodable file, no detectable face, or more than one detectable face. Appearance is never a blocking reason. Rules that are not checkable from an image are neither blocked nor warned; they appear as static guidance in the upload manual.
- **Reasoning**: Blocking and warning demand the same corrective action from the candidate -- retake the photograph -- so blocking buys no additional protection while removing the deliverable. The error costs are asymmetric: a wrong warning is an annoyance, a wrong block is a lost user on a false premise. That asymmetry is decisive for the appearance signals specifically, because detector reliability is uneven and, for head coverings, the rules themselves conflict: IBPS, GATE and the Navy expressly permit religious headwear that SSC prohibits, so a blanket cap block would wrongly reject candidates on examinations that allow them. Multiple faces is a block rather than a warning because selecting a face would silently produce a photograph of a possibly different person, which is an untruthful output rather than a risky one.
- **Consequences**: The engine's public contract is that it never refuses for appearance reasons. Deterrence is delivered by the web app instead: `likely_rejection` presents an acknowledgement step with retaking as the primary action and downloading as a secondary one, while `possible_issue` is an inline notice. This separation is deliberate -- "the engine refuses" and "the interface asks you to confirm" are different guarantees, and only the second is safe when a detector can be wrong. Detectors will be introduced in confidence order (eye closure first, since the vendored face landmarker already emits blend shapes; sunglasses and head coverings require classifiers that do not yet exist), and no signal may be promoted to `likely_rejection` before its reliability is measured.
- **Affected Modules**: `services/image-engine/src/exam_photo/suitability/`, `services/image-engine/src/exam_photo/orchestration/rule_pipeline.py`, `apps/web/src/components/`.
- **Approval Owner**: Lead Architect
- **Amended 2026-08-04 (no stage may block for composition reasons)**: Wiring the policy into `process_rule` showed the contract was being contradicted from inside the pipeline. Two photographs the policy had already judged acceptable still produced nothing, because background composition treated `BACKGROUND_FOREGROUND_TOO_SMALL` and `BACKGROUND_SUBJECT_CLIPPING_RISK` as hard failures. A subject that fills little of the frame, or whose hair reaches the top edge, is a composition concern rather than an unusable output -- and the approved reference outputs let hair reach or leave the edge on most photographs. Both are now warnings that surface as `possible_issue` findings and still produce a photograph. The rule is therefore stated more strongly than originally written: **no stage anywhere in the pipeline may block for an appearance or composition reason.** Only an undecodable file, no detectable face, or a genuinely ambiguous subject may refuse. Genuinely unusable mattes remain caught by segmentation mask validation, which is a different failure.
- **Amended 2026-08-04 (face counting)**: The original entry left the detector's "exactly one face" requirement in place. That requirement blocked a single candidate photographed in front of a printed banner, whose spurious second face appears only at the lowest confidence tier and carries no landmarks. Face counting is now delegated to the disposition policy, which weighs the second face's size and the tier it was found at, and the pipeline proceeds with the largest face when the subject is unambiguous. A related defect was fixed in the recovery ladder, which failed to record which confidence tier a multi-face recovery had used, making a desperation-tier detection look like a full-confidence one.
- **Amended 2026-08-04 (blend shapes)**: The original entry anticipated eye closure as the first detector to ship, "since the vendored face landmarker already emits blend shapes". Measurement contradicted this: the eye-blink score does not separate closed eyes or sunglasses from narrow or deep-set eyes. Blend shapes are switched off, no consumer exists, and eye closure remains unimplemented pending a real classifier.

### DEC-042: Per-Exam Appearance Rules With Three-State Policies
- **Date**: 2026-08-04
- **Status**: Approved
- **Problem**: Appearance rules were previously treated as platform-wide constants. Research over 48 Indian examinations shows they are exam-specific and frequently contradictory, so any hardcoded majority behaviour is wrong for a known set of examinations. Verified conflicts: background is white or light for most bodies but MPSC prefers solid blue, green or red; spectacles are prohibited during SSC live capture, permitted without reflections by banking bodies, permitted only if regularly used by NTA, and permitted as normal corrective lenses by GATE; smiling is prohibited by UPSC and Railways but expressly allowed by CBSE; a printed name and date is required by TNPSC, Kerala PSC and CBSE and expressly prohibited by Railways; colour is required by most bodies but CUET-PG and UGC-NET accept black and white; verified face-occupancy thresholds are 50%, 60-70%, about 75% and 80%.
- **Decision**: Extend the canonical JSON Schema in `packages/exam-rules` and its Pydantic mirror with an appearance block carried per exam. Policy fields that a boolean cannot express use a three-state enumeration -- `permitted`, `prohibited`, `conditional` -- with a free-text condition string, because "prohibited except for religious reasons" and "permitted only if regularly worn" are neither yes nor no. This applies at minimum to spectacles and headwear. Background colour, face-coverage target, colour-versus-monochrome acceptance, ears visibility, smile permission and the name/date imprint are likewise carried per exam rather than assumed.
- **Reasoning**: This is the "Exam First, Tool Second" principle applied to appearance: the exam rule record drives the pipeline, and the research establishes that no majority default is safe. A two-state flag would force every conditional rule to be recorded as either a false prohibition or a false permission, and the conditional cases are exactly the ones with the highest cost of error, since they cover religious head coverings and prescription eyewear.
- **Consequences**: Warnings become exam-dependent: the same photograph may warn for one examination and pass silently for another, which is correct. The name/date imprint is a rendering capability the engine does not yet have and is scheduled as real work rather than a validation check. Rules recorded as unverifiable in the research are represented as absent rather than as permissive defaults, consistent with the no-silent-assumptions principle. Public guidance must not assert that all examinations require a white background, prohibit smiling, or prohibit spectacles; the verified evidence contradicts each of those claims.
- **Affected Modules**: `packages/exam-rules/schema/exam-rule.schema.json`, `services/image-engine/src/exam_photo/models/exam_rule.py`, `services/image-engine/src/exam_photo/orchestration/rule_resolver.py`, `examples/rules/`.
- **Approval Owner**: Lead Architect

### DEC-043: Natural Enhancement Corrects the Capture, Never the Subject
- **Date**: 2026-08-04
- **Status**: Approved
- **Problem**: The product owner asked for basic, natural enhancement -- lighting, contrast, sharpening, noise reduction -- explicitly bounded as "not unnatural and dramatic or unreal" and "completely optional, only if required". The output preparer already had brightness/contrast/sharpness machinery, but its mode defaulted to `none` and its adjustment factors were caller-supplied constants: nothing measured the photograph, so nothing could decide whether enhancement was required or how much. The obvious implementation -- measure a "good" reference population and drive every photograph toward its mean -- is unsafe, and was rejected before being built.
- **Decision**: Enhancement corrects **capture defects relative to each photograph's own rendering**, and never moves a subject toward a target appearance. Four corrections are planned, each triggered only by its own measured deficit: a compressed tonal range is stretched; clipped shadows or highlights are recovered away from the clipped end; a non-neutral illuminant is partially neutralised; a soft capture is sharpened. Each is capped at the output preparer's existing conservative limits (0.12 brightness, 0.12 contrast, 0.20 sharpness). A photograph with no measured deficit receives a no-op plan, which is the common case. Every adjustment actually applied is disclosed to the candidate rather than performed silently.
- **Reasoning**: An absolute luminance target would lighten dark skin, which the identity-preservation principle prohibits outright -- so the trigger for brightness correction is *clipping*, and the trigger for contrast correction is *compressed range*, neither of which is a property of the subject's complexion. A correctly exposed dark-skinned face has a healthy tonal range and no clipping, and is therefore left completely untouched; `test_a_correctly_exposed_dark_face_is_untouched` asserts exactly that and is the load-bearing test of this module. The colour-cast trigger is likewise a property of the illuminant rather than the subject: human skin under neutral light is red-dominant, measured at 38 to 88 levels of red over blue across all 40 photographs in the adversarial set, so a face where blue approaches or exceeds red is coloured light rather than a complexion. Cast correction is deliberately partial (capped at half the measured excess) because fully neutralising a severe stage-lit cast invents colour the sensor never recorded.
- **Consequences**: A reviewer's "perfect"/"clean" labels record pose, quality and compliance, **not** lighting, and are explicitly barred from being used as a photometric target -- this is recorded in the label fixture so a later reader cannot mistake them for one. One photograph in the set carries a cast severe enough (blue minus red +58.8, against a next-worst +20.1) that correction alone cannot rescue it, so it is both corrected and warned about. Disclosure was chosen over silent application at the product owner's direction. Noise reduction is specified here but not yet implemented; the other three corrections are.
- **Affected Modules**: `services/image-engine/src/exam_photo/suitability/enhancement_planner.py`, `services/image-engine/src/exam_photo/providers/output_preparers/deterministic_output_preparer.py`, `services/image-engine/tests/fixtures/adversarial_label_map.json`.
- **Approval Owner**: Lead Architect

### DEC-044: The Bottom Edge Is Anchored to the Chin, Not Left Over
- **Date**: 2026-08-04
- **Status**: Approved
- **Problem**: The output-invariant sweep failed 224 of 960 generated geometries, every one of them on below-chin space, and 212 of those where the head box reached far above the face box -- voluminous hair. Below-chin space was not constrained anywhere in the engine. It was a residual: whatever head height and top margin happened to leave. On a subject with a high crown that residual is large and systematic. The eye line as a fraction of crop height is `(eye - crown)/span * head_height + top_margin`, and the crown-to-eye distance measures ~0.64 of the crown-to-chin span on such subjects, so the 0.86 head-height target forces the eye line to 0.60 -- past its 0.54 ceiling even at the minimum top margin. Because the eye line was a constraint and below-chin space was not, the search bought the eye line by shrinking head height, and the 0.19 of frame height that freed up drained out below the chin where nothing looked at it. Verified on a real failing case: head height 0.792 against an 0.86 target, top margin pinned at its 0.02 minimum, eye line 0.527, below-chin 0.188.
- **Decision**: State below-chin space as a constraint in the candidate search, bounded at 0.15 of crop height, and rank it **above** the eye line in `_RELAXATION_TIERS` so the eye line is surrendered first. The product rule this encodes, from the product owner, is that the bottom edge is anchored just below the last beard line -- or just below the chin if clean-shaven -- with a small margin, tightened further wherever the target dimensions allow; framing wins, and the eye line lands where the resulting frame puts it. The engine cannot detect a beard line (DEC-035 records three attempts rejected on measured evidence), so the anchor is the existing uniform chin-plus-margin floor, `_CHIN_BEARD_MARGIN_RATIO`.
- **Reasoning**: Below-chin space is not an independent degree of freedom -- `below_chin = 1 - top_margin - head_height` -- so the constraint adds no new axis to the search. What it adds is a *statement* of the rule. Left implicit in head height and top margin, the rule was silently invertible in exactly the case it matters. The bound at 0.15 is read off measurement on both sides: across the 60 approved ideal outputs, chin-to-bottom as a fraction of their own frame height is min 0.054, p25 0.081, median 0.102, p75 0.142, p90 0.179, max 0.247; across the ten engine outputs a reviewer assessed individually, every accepted photograph sat at or below 0.155 and the two rejected as too loose sat at 0.188 and 0.190. 0.15 therefore sits above ordinary approved framing and below both rejections and the 0.175 delivered invariant, leaving room for the candidate grid's integer quantisation, which moves head height ~0.02 per step.
- **Consequences**: The last relaxation tier deliberately does **not** waive `below_chin`, which is the one place the ladder is not cumulative. That tier adds exactly one constraint, `head_height_min`, and below-chin space does not conflict with it: head height is set by the crop's size and below-chin space by its position, so giving up the second buys nothing toward the first. Carrying it down anyway -- purely because the sets nest -- left 12 geometries delivering 0.20-0.21 while a 0.15 candidate sat unchosen at the same tier, the cost function having placed those crops on the padding term alone. Three validation regions moved with the search in the same change, per the defect class in DEC-029 and DEC-038: head-coverage validation and margin reporting are now keyed to `mandatory_box` under the search's own condition (adaptive planning, subject clipping disallowed) rather than to `outer_hair_relaxation_used`, which is only the weaker statement that no candidate happened to keep the whole preservation box. A crop could otherwise be selected as "strict", leaving that flag false, while its bottom edge sat correctly at the chin/beard line and well above the head estimate's bottom -- and validation then reported the planner's intended framing as a blocking `CROP_HEAD_CLIPPED`. Mask retention deliberately stays measured against the generous box: keyed to `mandatory_box` it would return 1.0 by construction on every crop the search can select, and a check that cannot fail is worse than no check. Sweep violations 224 -> 0; delivered below-chin space now measures min 0.082, median 0.110, p90 0.137, max 0.151. Six of the 60 approved ideals themselves exceed the 0.175 invariant, four in the 1200x1800 class where head height is bound by the target's width rather than by composition; the invariant is calibrated on the reviewer's verdicts over engine outputs and remains a report rather than a refusal (DEC-041).
- **Affected Modules**: `services/image-engine/src/exam_photo/providers/crop_planners/deterministic_crop_planner.py`, `services/image-engine/tests/orchestration/test_output_invariants.py`, `services/image-engine/tests/providers/test_crop_mode_a.py`, `services/image-engine/tests/orchestration/test_visual_regression.py`, `HANDOFF-INVARIANTS.md`.
- **Approval Owner**: Lead Architect
- **Amended 2026-08-04 (the preservation box has no bottom)**: The sweep reached zero while photograph 35 -- one the product owner had flagged by eye as too loose below the chin -- did not move a pixel. Instrumenting the candidate search on the owner's own review photographs showed why, and it was a larger defect than the one the entry was written for. The best candidate on every photograph measured was a fully compliant **tier 0** crop, and it was being discarded by the strict/relaxed preference, which prefers a candidate keeping the whole preservation box and applies that preference as an *override* rather than a tie-break -- a strict candidate wins outright whenever one exists, so the preference silently outranked every composition target the search had just scored. The clause responsible was `b_cand < preserve_box.bottom`. That box's bottom is not an observation of the subject: it is a fixed geometric expansion past the jaw, landing in the neck, so requiring the crop to reach it made the bottom edge a consequence of the head estimator's padding rather than of the candidate's anatomy. It is removed. The chin and beard boundary remain protected by `chin_protection_y` -- the landmark chin plus the beard margin -- as a hard constraint, which is the actual promise; the strict preference is about hair, and now covers only the crown and the two sides, as its own comment always claimed. Measured on the ten photographs labelled perfect in the 40-photo adversarial set, below-chin space as a fraction of frame height: photo 4 0.155 -> 0.081, 5 0.124 -> 0.104, 8 0.124 -> 0.105, 13 unchanged 0.117, 17 0.155 -> 0.111, 18 0.151 -> 0.117, 19 0.147 -> 0.098, 27 unchanged 0.111, 31 0.188 -> 0.146, 35 0.190 -> 0.111. Head height rose or held on all ten (35: 0.766 -> 0.857; 19: 0.823 -> 0.877; 4: 0.805 -> 0.862). All ten now satisfy every invariant, where two did not before. Photograph 31 remains the loosest at 0.146 because its subject's hair pins the crop's sides, which is the strict preference doing the job it is actually for. Across the synthetic sweep the delivered distribution tightened from min 0.082 / median 0.110 / max 0.151 to min 0.075 / median 0.103 / max 0.151, against an approved-ideal median of 0.102. **The general lesson is the one worth carrying: a preference expressed as an override is not a preference.** The strict/relaxed mechanism ranks before tier and cost, so anything folded into it is promoted above every constraint in the ladder, whether or not that was intended.

### DEC-045: One Composition, and Dimensions Chosen From the Photograph
- **Date**: 2026-08-05
- **Status**: Approved
- **Problem**: Encoding the 48-examination research exposed three defects that the previous rule set was too thin to reveal. (1) The crop profile was selectable per exam, and the Mode A default was the *loose* preset (0.60 head height) rather than the tight composition every approved output was calibrated to, so any rule that did not name a profile silently produced a looser photograph than the examination asked for. (2) The resolver had two branches -- exact and range -- for what is actually three cases, and the `else` branch treated "unspecified" as "the body published nothing". Twelve records in the research publish `200 x 230 pixels (preferred)`: a size that is published but not mandated. That combination had never existed in any rule record, because the earlier appearance research deliberately excluded file specifications, so every unspecified record carried no numbers at all. The new case fell into `else` and every one of those examinations was resized to a platform default instead of the number in its own notification. (3) Crop planning failed the whole pipeline whenever crop validation reported an error, and the errors in question were compositional -- head coverage under the exam's floor, mandatory head box not contained. A photograph the product owner had labelled perfect produced *nothing at all* on three of five real exam rules.
- **Decision**: One composition for every examination, with no fallback and no per-exam profile selection; `CropProfile` remains in the schema for reporting but no longer selects geometry, and per-examination deviation is expressed by overriding individual ratios with published evidence. Output dimensions are taken from a published preferred size when the body names one, and otherwise chosen per photograph from the crop's own geometry inside a 240-1200 px envelope, never from a constant. Crop planning blocks only on structurally unusable geometry -- no usable input, no resolvable target aspect, an aspect that does not match the one requested, or a provider failure -- and reports every composition shortfall as a warning while still delivering the photograph.
- **Reasoning**: A single tight composition loses nothing measurable. Across the 48 examinations not one publishes a face-coverage maximum a tight crop would breach; the only upper bound in the set (GATE, "60-70%") is stated on a different basis and is satisfied anyway, since a tight crop measures ~0.58-0.60 face height at 0.86 head height. What bodies publish is minima -- UPSC 75%, RRB 50%, NTA 80%, CBSE 80% -- which one tight composition clears. Where an exam's own dimensions make 0.86 unreachable, the relaxation ladder already returns the tightest crop the geometry allows (DEC-039); a looser profile was never the mechanism for that. Keeping the loose presets was worse than leaving them unused, because they omit four settings the tight one carries and a rule naming one fell back to defaults the tight profile's own comments record as wrong for exam framing. On blocking: refusing for a composition reason contradicts DEC-041 and delivers strictly less than the compromise it rejects -- the candidate gets nothing instead of the tightest crop available, which is worse on the published requirement and on every other axis.
- **Consequences**: `PLATFORM_DEFAULT_DIMENSIONS` and its resolver are removed as dead, and `platform_default_profile` is no longer required on an unspecified rule -- nothing reads it, so demanding it would force fifteen records to carry an inert value. The engine does **not** distort to reach a target: the output preparer refuses on an aspect mismatch beyond 1% rather than stretching, on both the exact and range paths, and the delivered aspect always follows the crop. Verified end to end on the owner's reviewed photographs across five rules spanning every dimension mode -- 20 of 20 outputs correct on pixel dimensions, byte ceiling, format and filename, against 16 of 20 before. Photograph 31 now produces output on every exam.
- **Affected Modules**: `services/image-engine/src/exam_photo/orchestration/rule_resolver.py`, `orchestration/rule_pipeline.py`, `models/exam_rule.py`, `scripts/encode_exam_rules.py`.
- **Approval Owner**: Product Owner

### DEC-047: The Examination Is a Deliverable Inventory, Not a Photograph Rule
- **Date**: 2026-08-05
- **Status**: Approved
- **Problem**: The product is pivoting from photograph preparation to exam-first application-upload preparation, and the schema cannot express the new product unit. A rule record is one examination, one stage and one photograph specification, and every consumer assumes that shape. The deliverables research covering the same 48 examinations counts roughly 48 signature items, 44 photographs, 15 thumb impressions, 13 handwritten declarations and about 40 certificate or identity scans across 50 stage-specific records: the photograph is roughly a quarter of what an application asks for. Two consequences were already visible in the catalogue. The four SSC examinations were dropped as "live capture only -- nothing for the platform to deliver", which was true of the photograph and false of the examination, since SSC requires an uploaded signature at 10-20 KB. And the RBI Assistant cycle needed two rule records with different IDs to express one examination with an uploaded and a live photograph.
- **Decision**: Add an optional `requirements[]` inventory to the rule record: one entry per item the examination asks for, carrying `requirement_type`, `submission_method`, `requirement_status`, `applicability`, `platform_support`, and -- for non-photograph items -- a `file_spec`. `image_requirements` stays exactly where it is, and the photograph requirement is forbidden from carrying a `file_spec` of its own.
- **Reasoning**: The plan this came from proposed relocating `image_requirements` under a photograph requirement. That was rejected on inspection: it touches ten source modules, the API contracts, the web types and about a dozen fixtures, regenerates all 39 records, and buys nothing functional while the non-photograph specifications are still half placeholder. Forbidding `file_spec` on a photograph requirement achieves the same guarantee the relocation was for -- exactly one place a photograph rule can live -- at the cost of one schema rule with a stated reason, rather than a rewrite of every caller against a shape that is still moving. `requirement_type` and `submission_method` are kept independent because a live portal photograph is a photograph submitted by live capture; folding the method into the type would make "how many photographs does this exam want" unanswerable. `platform_support` is a separate vocabulary from `exceptional_instructions.processing_support_status` rather than an extension of it: they answer different questions -- what the platform does for an item, versus how completely the photograph pipeline satisfies a photograph rule -- and one scale for two questions forces every consumer to know which subset applies to it.
- **Consequences**: Three model rules make the product's own boundary structural rather than editorial. A submission method the platform cannot execute (`official_live_capture`, `external_identity_verification`, `typed_or_selected_declaration`, `physical_stage_requirement`) cannot be marked `supported` or `partially_supported`; `platform_support: supported` on a non-photograph item requires a `file_spec` carrying at least a size or a format, so "supported" cannot be claimed with nothing behind it; and a conditional requirement must state its applicability, on the same reasoning as the conditional appearance policies in DEC-042. All 56 existing rule records validate unchanged, and `requirements` is absent from every one of them -- absent meaning the deliverable research has not been done for that exam, never that the photograph is the only requirement. Extending `is_valid_field_path` to reach into the new array exposed a latent defect: it unwrapped only one layer of type annotation, so every provenance path through an `Optional[List[Model]]` field was reported invalid. Now fixed for all such fields, not just this one.
- **Affected Modules**: `packages/exam-rules/schema/exam-rule.schema.json`, `services/image-engine/src/exam_photo/models/exam_rule.py`, `services/image-engine/tests/test_exam_requirements.py`.
- **Approval Owner**: Product Owner

### DEC-048: An Interim Placeholder Is Not a Platform Default
- **Date**: 2026-08-05
- **Status**: Approved
- **Problem**: The deliverables research establishes *what* each examination requires but frequently not *to what specification*. Of 48 signature deliverables, 25 carry a published file size and 23 do not; 13 of 15 thumb impressions do; all 13 handwritten declarations do. The product owner has directed that missing figures be filled with an average until the real ones are supplied. That instruction is in direct tension with the standing rule that a field recorded as `not_found` is omitted and never defaulted, because an absent rule and a permissive rule are different statements. Filling it silently would put values into rule records that no source supports and nothing marks.

For the signature gaps specifically, the interim value is the modal published specification, **10-20 KB, JPEG** -- not the arithmetic mean.
- **Amended 2026-08-05** (implementation, DEC-049): the status rule is scoped to interim entries on `image_requirements.*` paths. As first written it covered every path, and encoding the inventory showed that to be wrong: a placeholder signature size would have demoted all 32 `verified` and `verified_with_ambiguity` records to `provisional`, none of which says anything about how well those examinations' *photograph* rules are evidenced. `status` has always been a statement about the photograph specification -- it is what the catalogue tiers, the gap register and every current consumer read it as -- so that is what the rule now governs. A requirement's own specification quality is carried by its own provenance entry, equally findable by the same query. When requirements grow a per-item status, this scoping is the thing to revisit.
- **Reasoning**: The instruction is followed; only the statistic and the labelling are chosen to make it safe. On the statistic: the mean across the 25 published records is 10.6-45.2 KB, and a 45 KB signature exceeds the ceiling at SSC, banking, JEE Main, UGC-NET and CTET -- five of the six distinct published specifications. Overshooting a maximum is a hard portal rejection; undershooting is usually harmless. The modal specification, 10-20 KB, falls inside five of the six published ranges, missing only UPSC's 20 KB floor. So the mean is the wrong statistic for a ceiling, and the right one is also the most common one. Dimensions are deliberately *not* averaged: the two published signature dimensions are 140x60 and 580x180, different aspect ratios, and averaging them would invent a shape no body publishes -- those records take `dimensions.mode: unspecified` and size from the source, exactly as the 15 size-only photograph records already do. On the labelling: `platform_default` already exists but means a settled policy choice the platform stands behind, such as the decimal reading of "KB". An interim value is known to be wrong-until-replaced. Collapsing the two would make every placeholder unfindable the moment the real figures arrive, and a placeholder that cannot be found is how it quietly becomes a fact.
- **Consequences**: Replacing the placeholders later is a query rather than an excavation: `type == interim_default` enumerates them exactly, and the status rule guarantees none of them is sitting inside a record presented as verified. The constraints are enforced in the Pydantic model, so the encoder, the rule-admin console and the `POST /v1/rules/validate` endpoint all reject a mislabelled placeholder identically. No interim value is written yet -- this decision establishes the mechanism; the encoder pass that uses it is separate.
- **Affected Modules**: `packages/exam-rules/schema/exam-rule.schema.json`, `services/image-engine/src/exam_photo/models/provenance.py`, `services/image-engine/src/exam_photo/models/exam_rule.py`.

### DEC-050: On Paper, Correct Aggressively; On a Face, Barely at All
- **Date**: 2026-08-05
- **Status**: Approved
- **Problem**: The pivot adds signature, thumb-impression and handwritten-declaration deliverables, and the product owner's requirement is that a phone photograph of ink on paper -- underexposed, pale yellow, shadowed, blurry -- must come out looking like a clean scan: black or blue ink on pure white. The existing photograph pipeline cannot do this and must not be taught to: DEC-043 deliberately restrains correction to what a capture needs, because on a face anything stronger starts altering the subject. Applying that restraint to paper would deliver the yellow shadowed original; applying the paper treatment to a face would be exactly the identity modification AGENTS.md prohibits.
- **Decision**: A separate `exam_photo.ink` package with the opposite tonal rule. The paper's illumination is estimated and divided out, the paper is driven to pure white, and the ink is driven to full strength. **Stroke geometry is never touched** -- no thinning, thickening, smoothing, straightening, joining or redrawing. The mark's identity is its shape; the tonal curve moves brightness only. The handwritten declaration goes through the same path with no content understanding at all, per the owner's ruling: no OCR, no comparison against required text, no missing-word detection.
- **Reasoning**: The two rules are opposite because the subjects are opposite. A face carries information in its tones and the person is the subject; paper carries no information in its tones and the *mark* is the subject. Writing this as a separate package rather than a mode on the existing preparer keeps that from being "simplified" later by someone reasonably assuming one enhancement policy should serve both. Four measured decisions inside it, each taken against the reference photographs rather than from first principles: (1) illumination is estimated on a coarse tile grid, not by max-filtering, because a max-filter background reads a thumb impression's interior as paper and erases the impression from its own centre outward -- measured, a 9-pixel max filter left the impression at luminance 160-200 against paper at 255; (2) ink depth is measured on the channel *minimum*, not the maximum, because a blue ballpoint keeps a bright blue channel and scores 0.698 by maximum against 0.894 for an identical black signature, while by minimum they score 0.903 and 0.902; (3) the ink threshold is relative to the darkest mark present, set at 0.55, chosen by sweeping it until the hard photograph's ink coverage landed inside the two approved outputs' range rather than above it, which is the point at which the receipt's show-through stops being counted; (4) the depth reference is the 99.9th percentile rather than the 99th, because a signature in the corner of an A4 sheet covers under 1% of it and the 99th percentile would then measure paper and report the page blank.
- **Consequences**: On the reference set, all five inputs deliver paper at median 255 with the mark's own colour preserved. Both approved outputs are reproduced closely -- crop aspect 3.94 against a source 4.00, and 3.48 against 4.64 -- and both thumb captures crop tightly to the impression. The show-through on the hard photograph is removed entirely and the hand holding the sheet is rejected. **Framing on that photograph is not solved**: the crop comes out roughly 1.7x the signature's extent because the sheet's own edge survives as a line of ink-classified pixels. The delivered file is usable and merely loose, so this is recorded as a bound with a ratcheted test rather than treated as blocking. Two further limits are recorded rather than hidden: a gradient harsher than about 25% across the page is reduced rather than removed, because a tile is described by its brightest content and the outermost half-tile has nothing beyond it to interpolate against; and no pencil or dried-out-pen sample exists in the reference set, so the faint end of the ink threshold is untested. Three fixes were made only because the reference photographs contradicted the first implementation -- the channel-maximum depth, an unrestricted hole fill that adopted a whole finger as paper, and an edge-connectivity rule that deleted an entire cursive signature for grazing the sheet edge and took ink coverage from 5.44% to 0.65%.
- **Amended 2026-08-05** (product owner review: "awful, cannot be used"): the rendering step was rebuilt and two defects behind that verdict were found by looking at the outputs rather than at the metrics, which had reported paper at 255 and ink coverage in range throughout. (1) The renderer composited ink opacity against a *single flat ink colour*. On a signature that merely thinned the strokes; on a thumb impression it was destructive, because an impression is a continuous field of density whose entire value is the ridge pattern in the mid-tones, and collapsing every tone onto one colour shredded a solid inked oval into blotchy speckle. Replaced by a per-channel levels stretch, which is monotonic and therefore keeps every tonal distinction while still driving paper to white and ink to full strength. (2) Pixels rejected as not-the-document -- the finger holding the sheet -- were excluded from the crop-box calculation but never from the pixels, so the finger was still drawn inside the crop as a large grey smear. Rejected regions are now forced to paper. A third change followed from the first: the white point moved from the ink threshold to just above paper grain, because clipping at the ink threshold erases an impression's lighter half by construction, and removal of show-through was handed to the ink mask, which can tell faint ink from faint bleed where a brightness cut-off cannot. A local-density filter was also written to clear the sheet-edge residue that keeps the hard photograph's crop loose, then **removed**: measured over the two regions at three window sizes, the density distributions overlap almost completely (signature median 0.289 against edge median 0.231 at 11x11) and the edge carries 2,243 ink pixels against the signature's 2,226 -- it is a line as substantial as the writing, not sparse residue. The measurements are recorded where the filter was.
- **Amended 2026-08-05, second review** (product owner: the impression "has lost its details in many places... leave the thumb impression as it is -- resize, crop, enhance a bit... harden the signature"): the single treatment is split in two, because the two deliverables want opposite things and one compromise served neither. A **mark** -- signature or handwritten declaration -- is a few strokes on a page where everything else is noise, so clearing the page outside the detected ink is most of the value and costs the mark nothing: a stroke is either there or it is not. An **impression** is the reverse: the deliverable *is* the ridge pattern, it lives in a continuous range of density, and every decision of the form "this pixel is ink and that one is not" removes some of it. Measured, clearing the page under the mark treatment punched visible holes through the pattern. The impression treatment therefore applies no ink mask at all and only corrects the capture -- lighting, crop, a gentle levels balance. Its white point was swept against paper cleanliness (median delivered paper 194/200/207 at depths 0.03/0.06/0.09) and set at 0.09, the cleanest value that changes nothing about the impression itself. Separately, the framing defect on the hard photograph is **closed**, by the test that finally separates the sheet's own edge from the writing: proximity. The edge runs along the boundary of the page while the signature sits in the middle of it, with bare paper between, so marks are grouped by proximity and small distant groups are dropped. That is the right shape of test -- "is this part of the writing" is a question about company, not about darkness, thickness or density, which is why the three earlier attempts failed. The hard photograph's crop went from 784x467 to 506x218 against a signature extent of about 430x110, and the equivalent synthetic case from 882x915 to 464x165 against an ideal 470x170; the ratcheted bound that recorded the defect is replaced by a real assertion.
- **Amended 2026-08-05, third review** (product owner: "still, some details are lost... the edges and a bit from the actual part"): the impression's white point was still cutting into the subject, and by a far larger margin than the previous amendment assumed. An impression fades outward -- its edge is genuinely faint ink rather than a boundary -- so any white point clips real detail. Measured as the share of non-paper pixels erased on the two reference impressions: 51.7% and 74.6% at depth 0.09, 40.4% and 69.3% at 0.06, 15.1% and 41.8% at 0.03, 9.2% and 22.0% at 0.02, and nothing at 0.01. **0.09 had been chosen by sweeping for the cleanest paper, which is the wrong quantity to optimise** -- it was discarding three quarters of the impression to make the background whiter, and the loss was visible immediately to the reviewer while every metric being watched stayed green. The clip now sits at 0.01, where it removes nothing; the paper needs no help, since flattening already leaves it at median 248 and third-quartile 252. The crop also gains a wider margin for impressions (0.08 -> 0.17 of the box's longer side), because the ink box is drawn where the impression crosses the ink threshold and the impression continues past that as fading ridge detail. Two tests now hold both: that faint mid-tones survive in quantity, and that an impression is framed wider than its threshold box. The general lesson is recorded here because it recurred three times in one session: on this deliverable, every metric that improves by removing content will read as an improvement, and only the eye catches it.
- **Amended 2026-08-06** (product owner: strokes broken -- "D, G some parts of the alphabets are missing" -- and a standing concern that the whole thing is tuned to five photographs): two fixes and a capture-robustness sweep. **Broken strokes**: detection and rendering were sharing one threshold, and they are different questions. Detection asks "is there writing here" and must be strict or show-through passes; rendering asks "is this pixel part of the writing that was found", and under the strict answer the thin part of a stroke -- a curve, a skip where the ball lifted, the fade at the end of a letter -- fell below the bar and was cleared as background, so letters arrived with holes. Rendering now keeps anything reaching 0.28 of the deepest ink *provided it adjoins accepted ink*; the adjacency is what stops the looser bar from readmitting show-through, which by construction covers the parts of the page the writing does not. Black-point headroom for marks also drops from 1.15 to 0.90, so a stroke's core clips solid rather than reading grey. **Robustness**: `tests/ink/test_ink_robustness.py` sweeps ~100 synthetic captures over ink colour and strength, exposure, colour temperature, uneven light, paper tone, capture distance, focus, sensor noise and show-through, asserting only structural properties -- not blank, crop contains the mark, paper light and mark dark, and for impressions that tone survives as a range rather than collapsing to two levels. The assertions are deliberately weak, because strong ones would be assertions about synthetic images. It found two real defects immediately. A **five-line declaration lost its lower lines**: proximity grouping bridged 0.025 of the longer edge, which merges a signature's letters but not a paragraph's line spacing, so the shorter lines became their own clusters and failed the mass test; the gap is now 0.05, measured to sit between the line spacing that must be bridged (0.048) and the sheet-edge distance that must not be (0.12). And **grouping ran twice at two different scales** -- once to choose the crop, once inside it -- so a declaration could be cropped correctly and then have its final line rendered blank, because the same page cropped is a different working scale from the same page whole. Grouping now runs only for crop selection: once the crop is made, what it excluded is already gone, and repeating the test inside the frame can only remove content the first pass decided to keep. One fixture bug was also found and is worth recording, because it nearly became a false finding: the sweep's "underexposed" case dropped the paper level while holding the ink colour fixed, which is not a dark photograph but pale ink on grey paper. A real underexposure scales ink and paper together and preserves their ratio. Exposure is now a multiplier applied last, and "grey paper" and "pale ink on grey paper" are separate cases under their own names. The sweep is marked `ink_robustness` and runs as its own CI stage, like the model-backed suites, so the fast subset stays fast.
- **Affected Modules**: `services/image-engine/src/exam_photo/ink/`, `services/image-engine/tests/ink/`.

### DEC-051: A Deliverable Is a File, Not a Picture
- **Date**: 2026-08-06
- **Status**: Approved
- **Problem**: `exam_photo.ink` produced good images and the catalogue said `not_yet_supported` for every one of them, correctly: an image is not a deliverable. IBPS asks for a signature at 140x60 pixels, 10-20 KB, JPG, named `signature.jpg`; the engine returned a 506x218 PNG. Nothing resized, compressed, named or checked it.
- **Decision**: `orchestration/deliverable_pipeline.py` -- normalise the upload, prepare the content by treatment, resize to the published dimensions, compress to the published ceiling, apply the published filename. Stages one, three, four and five are the existing providers unchanged; the photograph pipeline had already solved "make this file satisfy a specification" and the only thing missing was something to put in front of it. A third ink treatment, `PAGE`, is added for whole documents at the product owner's ruling that a handwritten declaration is a full page.
- **Reasoning**: `PAGE` differs from the other two on framing rather than tone: the deliverable is the sheet, not what is written on it, so it is never cropped to its content -- a declaration cropped to its writing loses the heading above and the date below, and a certificate cropped to its text loses the seal. Tonally it is the most conservative of the three, because a document can carry faint content that matters (a light stamp, a watermark, a carbon impression) and clipping that away alters the document rather than correcting the capture. Two integration problems were found by running real specifications through it, and both are recorded where they were fixed. The shared output preparer rejects an aspect mismatch beyond an *absolute* 0.01, which is about 1.3% relative at a photograph's 0.75 aspect and 0.43% at a signature's 2.33 -- so every signature was refused. Rather than loosen a bound the photograph pipeline depends on, the deliverable pads its frame to the target aspect first, which is the correct operation anyway: the white space around a signature is arbitrary, a face's margin is not. And IBPS publishes a 10 KB *floor* alongside 140x60 pixels; a clean two-tone mark over 8,400 pixels measures 3.0 KB at quality 95 and 7.1 KB at quality 100 with chroma subsampling off, so the floor is unreachable by a factor of about 1.4. The pipeline takes the last honest step and reports the shortfall. It deliberately does not pad the file with metadata to clear the number: that would satisfy a byte count with bytes that are not the signature, and would undo the metadata stripping that exists for privacy.
- **Consequences**: 104 of 155 requirements are now `supported`, up from 39 -- 37 photographs, 39 signatures, 15 thumb impressions and 13 handwritten declarations. Certificate scans and identity documents stay `not_yet_supported` on purpose: the engine can clean and frame a photographed page, but portals overwhelmingly want a certificate as PDF and nothing here writes PDF, so claiming support on the strength of producing a JPEG would promise a file the portal will not take. The encoder additionally withdraws a support claim when the record carries no size and no format to prepare against, so "supported" never outruns the evidence. The test asserting that no non-photograph deliverable claims support was correct when written and is now wrong; it is replaced by one asserting that only the served types claim it, plus one asserting every supported deliverable has a specification behind it.

### DEC-052: A Scan May Be Re-encoded; A Document May Not Be Re-rendered
- **Date**: 2026-08-06
- **Status**: Approved
- **Problem**: Certificates, mark sheets and identity documents are the deliverables most often required as PDFs, and 33 requirements were held at `not_yet_supported` because nothing here could write or read one. Candidates arrive holding one of two things: a photograph of a piece of paper, or a PDF somebody else made. The two are not the same problem.
- **Decision**: A new `exam_photo.pdf` package with three parts. `assembly` wraps pages the platform prepared itself into a PDF and searches for the byte ceiling, giving up quality before resolution. `inspection` reads an uploaded PDF and classifies each page as a *scan* or a *document*. `preparation` restructures an existing PDF -- strips metadata, recompresses streams, and re-encodes page images **only on pages classified as scans**. `pypdf` is added as a dependency; it is pure Python and BSD licensed, where PyMuPDF is faster and can rasterise but is AGPL, which is not compatible with shipping this commercially.
- **Reasoning**: The classification is the whole design. A scan is a photograph in a PDF wrapper, so re-encoding and downscaling it is the same operation the photograph pipeline already performs. A digitally issued certificate holds real text and vector marks, and rasterising that to hit a byte ceiling destroys exactly what makes it verifiable -- while succeeding on every number being watched. That is the failure mode this package exists to prevent, so it is refused structurally rather than avoided by care. Pages are classified by *area* rather than by image count, because "has an image" is true of nearly every generated certificate: they carry a seal, a logo, a photograph of the holder. What distinguishes a scan is that one image *is* the page, and that it yields no extractable text. Measured on the two real PDFs available, both a board mark sheet and an Aadhaar letter are full-page images with zero extractable text, so both classify as scans correctly. Resolution is spent only after quality on both paths: a soft full-size page stays readable, a sharp shrunken one may not, and for a certificate legibility is the entire purpose of submitting it.
- **Consequences**: 135 of 155 requirements are now `supported`, up from 104 -- the 31 certificate scans join once a PDF path exists. Measured on the real mark sheet, 1,670 KB reduces to 393 KB under a 400 KB ceiling at 65% of scanned resolution, to 172 KB under 200 KB, and to 95 KB under 100 KB; the Aadhaar letter passes a 400 KB ceiling untouched and reduces to 45 KB under a 50 KB one. Three routes exist through the deliverable pipeline and the third is a refusal: an image becomes a PDF, a PDF is restructured to a PDF, and a PDF where the requirement wants an image is prepared as a PDF with a finding saying so, because converting it would turn the document into a picture of itself. `FormatsConfig` now accepts `pdf`, and `ImageRequirements` refuses it -- one config type serves both, so the constraint sits where the distinction is known. Metadata is cleared by setting the whole dictionary to `None` rather than writing an empty one, because pypdf stamps itself as `/Producer` otherwise, and "made by pypdf" is still a fact about the candidate's toolchain travelling to an examination body. Page limits are reported and never enforced by dropping a page: choosing which page of someone's certificate does not matter is not a decision this software makes.
- **Affected Modules**: `services/image-engine/src/exam_photo/pdf/`, `orchestration/deliverable_pipeline.py`, `models/exam_rule.py`, `packages/exam-rules/schema/exam-rule.schema.json`, `scripts/encode_exam_rules.py`, `services/image-engine/tests/pdf/`.
- **Amendment (2026-09-11)**: The web app adds a PDF-to-image tool, at the product owner's request, and it does not reverse this decision. It runs entirely in the candidate's browser with pdf.js (`pdfjs-dist` 6.3.289, Apache-2.0, loaded only when the tool is used): nothing is uploaded, and the engine's automatic path still never rasterises a document. The difference is who decides. When a portal demands a JPEG of a certificate the candidate holds as a PDF, converting it is the candidate's call about their own document, on the same reasoning DEC-053 applies to removing a page. The tool states the cost plainly next to it: an image of a digitally issued certificate can't be verified the way the PDF can, so use it only when the portal asks for an image. Pages render at a chosen 100, 150 or 200 dpi over a white ground, as JPEG or PNG, up to 30 pages and 20 MB. A page that fails to draw keeps the pages already drawn and is retried from that page; a file pdf.js reports as invalid is not offered a retry. A PDF that needs a password to open is turned away with a direction to upload a copy without a password, and the product never asks for the password (product owner, 2026-09-11: a password step is friction for students). The same check runs in the browser before any PDF is uploaded for preparation or arrangement, through pdf.js rather than a scan of the file's bytes, so a PDF whose encryption opens with no password, which the engine also accepts, is not turned away; if pdf.js cannot load, the file goes to the engine, which refuses a locked PDF on its own: the arranger leaves it out with the same direction, and single-file preparation raises `PasswordProtectedPdfError`, recorded as `not_produced` with issue code `PDF_PASSWORD_PROTECTED` and no output file, so the quote classes it `nothing_prepared` and it can never be priced. Until then no locked PDF was recognised as locked: `inspect_pdf` read the absence of an exception from pypdf's `decrypt("")` as success, but pypdf reports a wrong password by returning `NOT_DECRYPTED`, so every locked PDF went on to read its pages and failed as undecodable. Single-file preparation told the candidate the file could not be decoded, and the arranger showed pypdf's own error text. The same misreading in `_rewrite` and in document assembly is corrected with it. Affected: `services/image-engine/src/exam_photo/pdf/inspection.py`, `services/image-engine/src/exam_photo/pdf/preparation.py`, `services/image-engine/src/exam_photo/pdf/document.py`, `services/image-engine/src/exam_photo/orchestration/deliverable_pipeline.py`, `services/image-engine/src/exam_photo/api/service.py`, `apps/web/src/components/exam/outcome-result.tsx`, `apps/web/src/lib/pdfjs.ts`, `apps/web/src/components/exam/requirement-upload.tsx`, `apps/web/src/components/exam/pdf-to-image.tsx`, `apps/web/src/lib/pdf-image.ts`, `apps/web/src/components/exam/document-workspace.tsx`.

### DEC-053: The Candidate Arranges Their Own Document
- **Date**: 2026-08-06
- **Status**: Approved
- **Problem**: A certificate is rarely one page. A mark sheet has a front and a reverse, a degree comes with a consolidated statement, an experience letter runs to three sheets. The candidate photographs them one at a time in whatever order they picked them up, and often has a PDF already covering some of the pages. Assembly handled a fixed list of prepared images and nothing else: no adding a page to an existing document, no fixing the order afterwards.
- **Decision**: `pdf/document.py`. `plan_document` flattens a list of uploads into a list of pages, each with a stable identity of (source index, page index) and an origin. `assemble_document` takes that list back in whatever order the caller gives, with any page rotated, repeated or omitted, and lands the result under the byte ceiling.
- **Reasoning**: Order is expressed as a list of page references rather than by mutating anything, so a page's identity survives being moved -- which is what a reordering interface needs and what makes the operation replayable. Removing a page is available *here and nowhere else*. The automatic path never drops one, because choosing which part of somebody's certificate does not matter is not a decision software should make; a candidate rearranging their own submission may obviously remove a page, because it is their certificate. Repeating a page is allowed for the same reason -- some portals ask for the same sheet twice. Rotation is stored as PDF page metadata, so it costs nothing and loses nothing.
- **Consequences**: An unreadable upload is recorded against its index and the remaining uploads still assemble, because one damaged file among five should not cost the candidate the other four. A requested page that does not exist is reported and skipped rather than raising. Nothing readable at all is the one hard error: an empty PDF is not a deliverable. Assembled documents carry no metadata, on the same reasoning as DEC-052. 15 tests cover planning, ordering, rotation, omission, repetition, mixed photograph-and-document assembly, and the text-page rule under an impossible ceiling.

### DEC-054: ONNX Export of BiRefNet as the Default Matting Backend
- **Date**: 2026-08-06
- **Status**: Approved
- **Problem**: A photograph takes 30-40s on CPU end to end. BiRefNet is roughly 12s per inference pass on CPU, and DEC-040 runs it twice per photo (whole frame, then the crop region at native resolution), so matting is the dominant cost. The product owner asked for this specifically, capped at a 10-12s target, with an explicit instruction not to trade quality for speed.
- **Decision**: Export the vendored PyTorch BiRefNet checkpoint to ONNX (`scripts/export_birefnet_onnx.py`) and add it as a third selectable `matting_backend`, `"birefnet_onnx"`, implemented by `providers/segmenters/birefnet_onnx_segmenter.py` against the same `SubjectSegmentationProvider` contract as the PyTorch backend. Same weights, same maths, no quantisation and no architecture change -- only the runtime executing the graph differs. `"birefnet_onnx"` becomes the default for `RuleOrchestratedPipeline`, the CLI, and the API's `"auto"` resolution (preferred over the PyTorch backend, which remains selectable). A new optional `matting-onnx` extra (`onnxruntime` only) lets a deployment run this backend without the ~600 MB of torch/transformers/torchvision/kornia/timm the PyTorch backend needs; that extra stays required for `scripts/export_birefnet_onnx.py`, since the export needs the original checkpoint as its source.
- **Reasoning**: The export was not a straightforward `torch.onnx.export` call and each obstacle is recorded because a future re-export will hit the same ones. (1) BiRefNet's decoder uses torchvision's modulated deformable convolution (`ASPPDeformable`), which has no ONNX symbolic anywhere. ONNX gained a native `DeformConv` op at opset 22, but onnxruntime 1.23 has no CPU kernel for it in either the standard or `com.microsoft` domain (confirmed by probing a minimal single-node model in both). The `deform_conv2d_onnx_exporter` package instead decomposes the op into ordinary `GatherND`/`Reshape`/arithmetic ops every runtime already implements -- the same algorithm restated in different ops, not an approximation -- so that is what is registered as the custom symbolic. (2) That package predates current PyTorch: it imports `JitScalarType` from a path that no longer exists, silently falls back to a broken legacy branch, and raises `KeyError`. The fix is supplying `torch.onnx.JitScalarType` to the already-present, already-correct "2.0 and later" branch it has -- a compatibility shim for an unmaintained dependency, not a change to the maths. (3) Some of the decoder's reshapes compute their target size from `aten::size` + arithmetic on a patchified feature map rather than a literal constant, so the traced graph carries no static shape for a few `DeformableConv2d` call sites even though the fixed 512x512 export input makes every size fully determined. The fix records each such call's true input shape from one eager forward pass (forward hooks, in call order) and only fills in a hole the graph left empty -- it never overrides a shape the graph did carry, and mismeasurement here has no way to hide, because it would show up directly as the equivalence check below failing on those photos.
- **Consequences**: Equivalence was proven, not assumed: the exported graph and the original PyTorch module were run on the same real photograph (`17-perfect`, `18-perfect`) with identical preprocessing, and the probability masks matched to a max absolute difference of 3.0e-5 / 3.5e-5 (tolerance 1e-3) -- the export writes `model-manifests/birefnet_onnx.json` recording this and refuses to write it at all if the check fails. End to end on the ten `perfect`-labelled photographs at 413x531 (`examples/rules/benchmark_exact_413x531_72dpi_white_bg.json`), warmed (one untimed call absorbs onnxruntime's one-time thread-pool/arena spin-up, ~100-150s on the very first inference of a process and never again): mean per-photo time fell from 21.38s to 10.64s, 1.85x-2.29x per photo, none regressing. Delivered JPEGs are pixel-equivalent to the PyTorch backend's: max channel difference 0-3 of 255 on at most 0.05% of pixels across all ten, one photograph (`35-perfect`) byte-identical. Photographs 17, 18 and 19 -- flagged for hair-edge complaints -- show no visible or measurable change; the matte quality this step touches is unchanged by construction, since it is the same computation. Raw inference alone (no pipeline overhead) measured 12.9s (PyTorch) vs 5.1-5.6s (ONNX), roughly 2.3x. Full CI-equivalent verification run: ruff format/lint and mypy clean; fast suite 274 passed; `mandatory_rule_pipeline` 30 passed; `mandatory_segmentation` 7 passed; `mandatory_refinement` 3 passed; `mandatory_engine_quality` + `mandatory_api` 11 passed; output-invariant sweep 0 violations of 960. Installed dependency footprint for a deployment using only this backend: `onnxruntime` is ~41 MB versus ~640 MB for torch + torchvision + transformers + kornia + timm + huggingface_hub, before either's own transitive dependencies.
- **Affected Modules**: `scripts/export_birefnet_onnx.py` (new), `model-manifests/birefnet_onnx.json` (new), `services/image-engine/src/exam_photo/providers/segmenters/birefnet_onnx_segmenter.py` (new), `orchestration/rule_pipeline.py`, `cli.py`, `api/service.py`, `api/settings.py`, `pyproject.toml`, `services/image-engine/tests/orchestration/test_rule_pipeline.py`.

### DEC-055: An Examination Is Named, Not Uploaded
- **Date**: 2026-08-06
- **Status**: Approved
- **Problem**: Everything the pivot built is library-only. `orchestration/deliverable_pipeline.prepare_deliverable` and `pdf.assemble_document` have no endpoint, and `api/app.py` serves `/v1/process` for a single photograph plus job status, output and rule validation. That was the stated blocker for UI work. Reading the service alongside the web app found a larger one underneath it: **the catalogue itself is unreachable**. Nothing under `services/image-engine/src` references `examples/rules/` -- there is no catalogue loader and no setting pointing at one -- and the web app's rule picker offers two bundled fictional samples plus a JSON file upload. `/v1/process` takes the entire rule as a form field precisely because the client was assumed to hold it. So the 39 encoded examinations and their 155 requirements are invisible to every caller, and the two highest-value screens -- the inventory, and the boundary between what the platform prepares and what it does not -- cannot be rendered at all, independently of whether the deliverable pipelines are exposed.
- **Decision**: Four steps, in this order. (1) Catalogue reads: `GET /v1/exams` and `GET /v1/exams/{exam_id}`, the latter returning the record with its `requirements[]`. (2) **One** preparation endpoint for every requirement -- `POST /v1/exams/{exam_id}/requirements/{requirement_id}/prepare`, multipart -- which resolves the rule, finds the requirement, and dispatches on `requirement_type`: a photograph to `rule_pipeline`, everything else to `prepare_deliverable`. (3) Documents as a call pair: one to persist the uploads and return `plan_document`'s pages, one to assemble them in the candidate's order. (4) The package. `/v1/process` is unchanged and retained.
- **Reasoning**: The ordering is forced by what is unreachable rather than by what is unbuilt. The kit screen renders from the catalogue and needs no pipeline at all, so exposing reads first unblocks more interface per unit of work than exposing preparation would, and it is read-only, needs no new storage and cannot regress the existing flow. On the single dispatching endpoint: the alternative -- keep `/v1/process` for photographs and add a sibling `/v1/deliverables/prepare` -- requires the browser to know which engine serves which requirement type. That is engine knowledge in the client, it duplicates `_TREATMENT_BY_TYPE` with nothing keeping the copy honest, and it inverts *Exam First, Tool Second*: a caller should name an item of an examination, never a pipeline. With one endpoint every tile in the kit is the same call, and the dispatch sits beside the mapping it depends on. `/v1/process` stays because the rule-admin console has a genuinely different need -- "here is an arbitrary rule, run it" -- and is the only caller that legitimately holds a rule the catalogue does not. Documents have to be two calls because a single call offers no point at which the candidate arranges anything, and DEC-053 built stable page identities precisely so they can; the uploads must therefore outlive one request, which is the only new storage requirement across the four steps, and it fits the existing job directory rather than needing a second abstraction.
- **Consequences**: Preparation is one request per item and there is deliberately no batch endpoint. Per-item requests give honest per-item progress with no worker queue, whereas a "prepare everything" button would be a single request of a minute or more, which would force asynchronous execution and with it the throughput work the product owner has reserved. **The synchronous choice carries a deployment constraint that must not be discovered in production**: a photograph is 30-40 s on CPU, nginx's default `proxy_read_timeout` is 60 s and Cloudflare terminates at 100 s, and a slow phone upload spends part of the same budget. The endpoint therefore has a real ceiling well below anything a local test will show. The existing `RECEIVED`/`PROCESSING` states, the job registry and `GET /v1/jobs/{job_id}` are already the escape hatch: if the ceiling bites, the preparation endpoint returns 202 with a job id and the client polls, with no change to the caller's mental model. That is a deployment decision rather than a throughput one, and neither is an invitation to optimise the pipeline. Separately, `examples/rules/` becomes a served directory while still being named as though it held examples; renaming it touches the encoder, the gap register and every path in the docs, so it is recorded here rather than done.
- **Amended 2026-08-06** (implementation): all four steps are built and the shape held, with three things the work surfaced. (1) **The download route was serving every output as `image/jpeg`.** That was correct while a photograph was the only thing this service produced and became wrong the moment a deliverable could be a PDF (DEC-052) -- a certificate would have arrived named `.pdf` and refused to open. The media type is now recorded on the job when the file is written, and an unrecognised extension falls back to `application/octet-stream` rather than to an image guess, because guessing image is the guess most likely to be wrong now that documents are in scope. (2) **A document's uploads are stored under generated names**, `source_0.pdf` and so on, never the candidate's own filename: it is attacker-controlled and would arrive as a legitimate-looking relative path, defeating the artifact store's traversal guard at the one point where the service writes a name it did not choose. (3) **Two requirements can publish the same exact filename**, and an archive that silently overwrote one with the other would hand the candidate a package missing a deliverable its own checklist claims to contain; colliding names are suffixed. The document pair is mounted under the requirement it belongs to (`POST /v1/exams/{exam_id}/requirements/{requirement_id}/documents`, then `POST /v1/documents/{job_id}/assemble`) so the support gate applies to both halves rather than only to the first.
- **Amended 2026-09-02** (the deployment ceiling was measured against a stale baseline): the Consequences above put a photograph at 30-40 s and treated the 202-plus-polling escape hatch as close to urgent. That figure predates DEC-054, which was merged on `main` the same day this entry was written on a branch cut before it. The measured time is **10.64 s** warmed, so nginx's 60 s default and Cloudflare's 100 s cut are no longer near, and the escape hatch is a scale-later decision rather than a near-term one. The reasoning for building it that way is unchanged -- per-item requests still give honest per-item progress with no worker queue. **One condition attaches**: the margin depends on the process being warm. onnxruntime pays a 100-150 s one-time spin-up on its first inference, nothing warms the service at boot, and `/health` reports healthy regardless, so a cold worker blows straight through both timeouts on its first request. The ceiling is therefore a readiness problem before it is a throughput one.
- **Affected Modules**: `services/image-engine/src/exam_photo/api/` (`app.py`, `service.py`, `contracts.py`, `settings.py`, `jobs.py`), `orchestration/rule_catalogue.py`, `apps/web/src/lib/api-client.ts`, `apps/web/src/lib/types.ts`.
- **Approval Owner**: Product Owner

### DEC-056: The Boundary Is Enforced Twice and Never Reduced to a Boolean
- **Date**: 2026-08-06
- **Status**: Approved
- **Problem**: `prepare_deliverable`'s own docstring states that it does not decide whether the platform should be preparing a requirement at all, and that the caller must filter out requirements whose submission method or platform support says otherwise. Once the API exists, that caller is a browser. A candidate believing the platform completed their SSC live capture is this product's worst failure mode, and it is a labelling problem rather than a technical one -- so leaving the filter in the client puts the entire boundary behind one layer of application code and one CSS class.
- **Decision**: Three rules. (1) The preparation endpoint refuses a requirement that is not `supported` or `partially_supported` with 409, carrying the requirement's own reason and guidance text rather than a generic error. (2) No response field anywhere collapses `platform_support` to a boolean; all five values travel to the client unchanged. (3) The client renders three outcome states -- clean, produced-with-caveats, blocked -- and the kit lists every requirement including the ones the platform will not touch, alongside the ten examinations the catalogue does not encode.
- **Reasoning**: The model already refuses to *record* an impossible support state: a submission method the platform cannot execute cannot be marked supported, and `supported` on a non-photograph item requires a `file_spec` behind it. The API refusing to *act* on one is an independent barrier rather than a duplicate -- the first governs what the catalogue may say, the second what the service may do, and a defect would have to occur in both to reach a candidate. On the boolean: a `can_prepare: true/false` field is exactly the mechanism by which `supported`, `partially_supported` and `guidance_only` become indistinguishable, and it delivers the failure mode through the contract rather than through the styling, where no amount of care in the interface can recover the lost distinction. `partially_supported` is the case that proves it -- TNPSC and Kerala PSC require a name and date printed on the photograph, which the engine cannot render, and a boolean has no way to say "a file, but not the whole requirement". On the third state: DEC-041 makes production the rule and refusal the exception, so `is_blank`, `findings`, `ceiling_was_unpublished`, `exceeds_ceiling` and DEC-051's unreachable-minimum message are all things the pipeline reports rather than raises. A two-state interface must file every one of them under success or failure, and a caveat filed under success is a caveat nobody reads. On visibility: the argument that keeps a `guidance_only` row on screen keeps an unencoded examination on screen too. A candidate searching SSC CGL and finding nothing concludes the platform does not cover it, while the register records ten examinations skipped for a *photograph* reason that between them still carry 23 non-photograph deliverables, all four SSC examinations among them. An absence the candidate discovers at the portal is worse than one admitted here, and in both cases the fix is a labelled row rather than a filter.
- **Consequences**: Of 155 requirements, 135 are `supported`, 16 `guidance_only`, 2 `partially_supported` and 2 `not_yet_supported`, so the gate refuses 18 and the kit displays all 155. The 16 guidance-only items are live captures and portal declarations, correctly never the platform's; they appear as instructions the candidate completes themselves and are visibly never a file the platform produced. The ten unencoded examinations appear as "not yet available" with the reason drawn from the gap register, and they remain the standing argument for letting a rule record exist without a photograph specification -- that fix is out of scope here, their visibility is not. Nothing carrying `guidance_only` or `physical_stage` may be counted as an output in the package, the checklist, or any progress indicator.
- **Amended 2026-08-06** (implementation): the requirement half needed no new data -- `platform_support` was already on every requirement -- but the *examination* half had no machine-readable source at all. The eleven unencoded examinations existed only as prose in `docs/EXAM_RULE_GAP_REGISTER.md`, and parsing a generated markdown table at runtime is not a source. `scripts/encode_exam_rules.py` now also writes `examples/rules/unavailable_examinations.json`, carrying each skipped examination's name, reason, detail and non-photograph deliverable count. Four decisions inside that. It is emitted **unconditionally alongside the markdown register rather than behind its own flag**, because an optional output is one a later regeneration forgets to ask for, and a picker that silently stops listing unavailable examinations looks exactly like a platform that dropped them. It sits in the catalogue directory rather than beside the markdown, because it is catalogue data and the service already resolves that one root. **All eleven are emitted, not the ten with deliverables**: the argument for showing them is that a candidate searching an examination and finding nothing concludes it is not covered, and that holds for the eleventh too -- the deliverable count then tells a consumer how much is actually at stake. And the API keeps them in a **separate list from the 39 selectable examinations** rather than merging them under a flag, since one list is selectable and the other is not, and a single list with a flag is how that distinction gets lost. Before the change, the encoder was verified byte-for-byte idempotent -- re-running it reproduced all 39 records and the register exactly -- so the regeneration added the sidecar and touched nothing else.
- **Affected Modules**: `scripts/encode_exam_rules.py`, `examples/rules/unavailable_examinations.json`, `services/image-engine/src/exam_photo/orchestration/rule_catalogue.py`, `api/app.py`, `api/contracts.py`, `apps/web/src/app/`, `apps/web/src/components/`.
- **Approval Owner**: Product Owner

- **Status**: Approved
- **Problem**: 86 values in the catalogue are `interim_default` -- a specification the platform chose because no body published one -- spread across 24 of the 39 examinations and sitting on 71 file sizes and 15 formats. DEC-048 built the label so that a placeholder could never quietly become a fact. It did not settle what a *candidate* is told. Showing a signature ceiling of 20 KB as though it were published asserts something no source supports; flagging it prominently states something the candidate cannot act on.

### DEC-058: The Kit Lives in the Browser, and Is Lost With It
- **Date**: 2026-08-06
- **Status**: Approved
- **Problem**: A kit is one examination's inventory in progress -- which requirements have been prepared, and which job holds each result. Requirements are completed in arbitrary order and potentially across several sittings, because a candidate has their signature to hand today and their caste certificate next week, so the mapping has to survive a page reload. The job registry is keyed by job and has no notion of a set.
- **Decision**: The `kit_id` and the requirement-to-job map live in `localStorage`. Artifacts stay on the server under the existing TTL and deletion machinery. Jobs carry the `kit_id` so the package endpoint can gather them.
- **Reasoning**: The alternative is a server-side kit record, which means a second identifier with its own lifetime, its own deletion semantics and its own relationship to the job TTL. Candidate photographs are sensitive personal data under the DPDP Act, where every additional retention surface is a liability to be reasoned about separately; putting the index in the browser and the artifacts under machinery that already expires and deletes them adds no new retention surface at all. `kit_id` on the job record is a grouping key rather than a record: it is written into the job manifest that already exists, and gathering a kit is a scan of manifests the registry already performs at startup.
- **Consequences**: **A candidate who switches device, clears their browser data, or opens the application in a private window loses their kit**, and the artifacts on the server become unreachable until the TTL removes them. This is recorded as a deliberate choice rather than left as an accident of implementation. It is judged acceptable for a guest purchase at a few rupees with no account: the recovery mechanism would be an account, an account is a larger product decision than this one, and a candidate mid-kit is minutes from finishing rather than days. It stops being acceptable the moment the product grows accounts, and this entry is the thing to revisit then rather than the `localStorage` code. One finding the reasoning surfaced and did not resolve: `job_ttl_seconds` defaulted to **3600**, one hour, so a kit spanning sittings is already bounded by the artifact lifetime rather than by the browser. Raising the TTL is a privacy decision to be taken on its own evidence and not a convenience knob, so it was recorded here as an open question rather than adjusted in passing. **Settled by DEC-066: thirty minutes**, which shortens the window a multi-sitting kit has rather than lengthening it -- the kit is bounded by the artifact lifetime more tightly than before, and that was accepted knowingly on the privacy side of the trade.
- **Affected Modules**: `apps/web/src/lib/`, `services/image-engine/src/exam_photo/api/jobs.py`, `api/service.py`.
- **Approval Owner**: Product Owner

### DEC-059: Published Rejection Conditions Are Routed, Not Assumed
- **Date**: 2026-09-02
- **Status**: Approved
- **Problem**: `rejection_conditions` was empty on all 155 requirements in the catalogue, so the exam pages could say what a file must be but never what gets it thrown out -- the half candidates actually fear. The data was not missing: the deliverables research carries 204 conditions across all 50 records, every one traced to the record's `evidence_source_url`. `extract_deliverables.py` wrote them to the sidecar and `encode_exam_rules.py` read the sibling `deliverables` array and never looked at them. The research records them **once per examination**; the schema attaches them **per requirement**. That mismatch is the whole of the problem: a signature condition shown against the photograph is a false statement about an examination's rules.
- **Decision**: Route each condition to the requirement type(s) it names, by keyword, in the encoder. Three rules follow from the data. (1) A condition naming several deliverables is attached to **each** of them. (2) A condition naming none goes to a new root-level `application_rejection_conditions`. (3) The report's null-statement -- "No additional explicit rejection condition was established beyond the active portal's format/size validation" -- is **dropped entirely**, never stored.
- **Reasoning**: There are only 19 distinct conditions behind the 204 occurrences, so routing could be checked exhaustively by hand rather than trusted in aggregate, and every one of the 19 is pinned in `tests/test_rejection_routing.py`. On multi-target conditions: "Unclear photograph, signature, thumb impression or declaration can lead to rejection" is genuinely about all four, and attaching it to one would understate the risk on the other three. On the root-level field: exactly one condition is application-wide -- "the online application is not registered unless all mandatory image fields are uploaded" -- and it is about the submission rather than any file, so forcing it onto a requirement would attach a true statement to the wrong thing, while dropping it would lose a genuinely useful warning. The addition is additive and both `additionalProperties: false` and `extra="forbid"` were updated together. On the sentinel: it is the research recording that it **looked and found nothing**. Storing an absence of evidence as a published rejection condition inverts it into an assertion about the examination -- the same error DEC-049 settled for rules, and what AGENTS.md means by no silent assumptions. **On the keywords**: word boundaries are load-bearing, not stylistic. "capital letters" contains "cap" and "that" contains "hat"; without `` the banking-family signature rule lands on the photograph as a headwear restriction. That is a wrong claim about an exam's rules, published on a page whose entire value is that its statements can be trusted, so it is tested rather than reviewed.
- **Consequences**: 84 of 155 requirements now carry published rejection conditions and 13 examinations carry an application-level one. Distribution by type: photograph 155, signature 31, handwritten declaration 26, thumb impression 13, certificate 3, identity document 1. The regeneration was verified surgical: 23 of the 53 records came back byte-identical and the only two key paths that changed anywhere in the catalogue were `/requirements[]/rejection_conditions` and `/application_rejection_conditions`, which is the evidence that the encoder stayed idempotent for everything else. In the interface these are attributed to the examination and never to the platform -- "Published by the exam, not by us" -- because a candidate who reads "we reject shadows" hears something different and wrong from "your exam rejects shadows". They are guidance and are never enforced: most are not checkable from a file at all, and DEC-041 makes production the rule and refusal the exception. **The keyword set is the standing risk**: a future research refresh introducing a condition phrased around a deliverable the cues do not name would route it to the application bucket rather than lose it, and a test asserts that nothing falls out of the router entirely.

### DEC-060: A Paid Output Never Comes From the Coarse Backend
- **Date**: 2026-09-05
- **Status**: Approved
- **Problem**: `_resolve_matting_backend`'s `"auto"` path preferred the ONNX BiRefNet backend, then the PyTorch one, then **fell back to MediaPipe**. The stated reason was that a machine which had not run the model acquisition scripts would still serve requests rather than failing every job, which is the right instinct for a developer setup and the wrong one for a product that charges money. `model-assets/` is gitignored, so *every* fresh clone and every new deployment host starts in exactly the state that triggers the fallback.
- **Decision**: `"auto"` resolves to `birefnet_onnx` or `birefnet` and otherwise **raises**, naming the three commands that fix it. MediaPipe remains selectable explicitly (`EXAM_PHOTO_MATTING_BACKEND=mediapipe`) for diagnostics and for the tests that assert against its coarse mask.
- **Reasoning**: Measured on one real photograph from the labelled set, same input and same rule, the two backends are not close: MediaPipe's 256px mask leaves stair-stepped edges with pieces bitten out of the ear and hair, while BiRefNet's is clean. The product owner's framing settles it -- "if we are charging people money for the output we need to be perfect about the generation". The candidate cannot tell which backend produced their file, has already paid by the time they could look, and may only discover it when a portal rejects the upload. **A job that fails loudly can be retried; a file that was paid for, submitted and rejected cannot.** This is the same principle as DEC-055's support gate: the platform refuses rather than quietly delivering something it would not stand behind. It is not in tension with DEC-041 ("produce, never refuse for appearance"), which governs judgements about the *candidate's photograph*; this is a judgement about the platform's own capability, which is the one thing DEC-041 does allow to block.
- **Consequences**: A deployment host without the weights now fails every photograph job at startup of the first request instead of serving degraded output, and the error names `download_birefnet.py`, `export_birefnet_onnx.py` and the `matting` extra. That is a deliberate trade: a loud failure during deployment is recoverable, a quiet quality regression in production is not. The ink deliverables (signature, thumb impression, declaration, certificate) are unaffected -- they never touch a matting backend, so a host without BiRefNet still serves those. `mediapipe` staying selectable keeps the existing marker-gated tests working unchanged.
- **Affected Modules**: `services/image-engine/src/exam_photo/api/service.py`.
- **Approval Owner**: Product Owner

### DEC-061: A Whole-Image Verdict Must Not Come From One Pixel
- **Date**: 2026-09-05
- **Status**: Approved
- **Problem**: `foreground_decontamination` reported `status=warning` on every photograph the product owner tested, and on all ten of the `perfect` set. The cause is one line: `EDGE_COLOUR_RECOVERY_OUTLIER` was raised by `np.any(diff > outlier_threshold)`, so a *single* pixel anywhere along the matte edge condemned the whole image. A real portrait has thousands of pixels in the uncertain-alpha band and at least one of them is always a large recovery step -- at a hairline against a contrasting background it is guaranteed. The warning therefore carried no information at all, which is worse than carrying none: a reader learns to skip it, and that is how a genuine decontamination failure reaches a candidate unnoticed.
- **Decision**: Judge the *share* of the recovered band that exceeds the threshold, not whether any single pixel does. Keep the code, and set the gate at `max_outlier_fraction = 0.35`.
- **Reasoning**: The share was measured before the number was chosen, across twelve photographs from the labelled set -- six `perfect` and six with a known flaw (cap, sunglasses, distant, off-pose, hoodie). Perfect ran 0.016-0.175; flawed ran 0.025-0.166. **The two ranges overlap almost completely, so the fraction does not grade matte quality and no threshold on it can.** That is the more important finding and it is recorded in the source beside the constant, because the obvious next move -- tuning the number until it separates good from bad -- cannot work and would cost someone an afternoon proving it. What the signal can still do is act as a tripwire: 0.35 is double the highest value any real photograph produced, so it stays silent in normal operation and fires only when propagation has gone wrong across a third of the band, which is a genuine failure rather than the ordinary cost of pulling colour across a soft edge. This follows the precedent already in HANDOFF for signals that were "built, measured, found not to separate, and removed" -- except here the computation is cheap and still useful as a failure detector, so it is retained rather than deleted.
- **Consequences**: Across the ten `perfect` photographs the outlier warning went from **10/10 to 1/10**, and the one that remains exceeds even the doubled threshold, so the signal now discriminates instead of firing constantly. `EDGE_DECONTAMINATION_UNCERTAIN` is a separate code with a separate meaning -- propagation could not reach every pixel within `max_search_distance` -- and is untouched; it fires on 2/10 and is left as real signal. **No delivered image changes.** This altered what is reported, never what is produced, and a parametrised test asserts that. Separately investigated and dismissed in the same pass: the product owner initially suspected crops were sometimes looser than they could be, then withdrew it on further inspection; measured head-height-to-crop across the ten ran 94.4%-115.1%, which is consistent with the estimated head box extending past the frame by design and showed no defect to fix.
- **Affected Modules**: `services/image-engine/src/exam_photo/providers/foreground_decontamination.py`, `services/image-engine/tests/providers/test_foreground_decontamination_outlier.py`.
- **Approval Owner**: Product Owner

### DEC-062: The Pipeline Is Built Once, Not Per Request
- **Date**: 2026-09-05
- **Status**: Approved
- **Problem**: The product owner reported the engine as too slow. Profiling the warm service showed 22.4 s per photograph, against the 10.64 s DEC-054 recorded, with 95% of it in two stages: `subject_segmentation` at 13.3 s and the DEC-040 crop re-matte (recorded under `mask_refinement`) at 12.4 s. But the same `segment_subject` call measured **5.5 s standalone**. The gap was not inference. `ApiProcessingService.process_job_sync` constructed a fresh `RuleOrchestratedPipeline` on every request, and with it a fresh onnxruntime `InferenceSession` over a 940 MB BiRefNet graph -- so the model was being loaded from disk for every photograph, twice over, and the cost was being attributed to inference by every timing anyone had taken.
- **Decision**: Build the pipeline once, lazily, and reuse it for the life of the service (`_get_pipeline`, guarded by a lock). Separately, give the ONNX session explicit options: `ORT_SEQUENTIAL` execution and `ORT_ENABLE_ALL` graph optimisation.
- **Reasoning**: Nothing about the pipeline varies per request -- every constructor argument derives from settings, which are fixed while the process runs -- so the per-request construction bought nothing at all. The segmenters already carry their own `RLock`, so a shared instance is what they were designed for, and FastAPI runs sync endpoints on a threadpool where that lock is exactly the right protection. On the session options, the configuration was measured rather than assumed, best-of-3 on a 1x3x512x512 input on an 8-logical-core machine: default 6.03 s, `intra_op=4` 5.59 s, `intra_op=8` 5.89 s, `intra_op=8` with `ORT_SEQUENTIAL` 4.78 s. Sequential wins because BiRefNet's graph is a deep chain with little node-level parallelism, so the inter-op pool costs more in scheduling than it recovers. Thread count is deliberately left to onnxruntime rather than pinned, because a number chosen on this machine would be wrong on a deployment box with a different core count.
- **Consequences**: **22.4 s to 10.1 s per photograph**, which lands on DEC-054's recorded 10.64 s and confirms the engine was never slow -- the service was. The same defect explains why CLI timings looked far worse still (44 s, and 89 s at 413x531): every CLI invocation is a fresh process and pays the same load, which is why a smaller output measured slower than a larger one and no resolution-based explanation ever fit. The remaining 10.1 s is two genuine BiRefNet inferences at roughly 5 s each; halving that again means not running the model twice, which is DEC-040's double matte and a quality decision rather than a performance one. **Memory cost**: one resident session for the process lifetime instead of one per in-flight request, which is a reduction under any concurrency. Surfaced but not caused by this work, and since **resolved**: `test_golden_images_regression` (marker `mandatory_rule_pipeline`) was failing on `case_marie_curie` with a composition complaint about the whole face being visible, and was recorded here as needing its own investigation. **It was a missing model asset, not a defect.** The golden-image test loads `selfie_segmentation.tflite` while the pipeline default uses `selfie_multiclass_256x256.tflite`; only the latter was installed. Fetching the `selfie_bin_general` variant makes it pass, verified 2026-09-06. This is the trap HANDOFF records under *Testing the engine locally* -- a missing second variant fails in a way that reads exactly like a composition regression -- and it cost a decision-log entry before it was understood, which is why the warning is worded as strongly as it is there.
- **Affected Modules**: `services/image-engine/src/exam_photo/api/service.py`, `services/image-engine/src/exam_photo/providers/segmenters/birefnet_onnx_segmenter.py`.
- **Approval Owner**: Product Owner

### DEC-063: The Preview Is the Only Image the Browser Gets Before Payment
- **Date**: 2026-09-06
- **Status**: Approved
- **Problem**: The web app declared `preview_url` and `preview_watermarked` on `PrepareRequirementResponse` and built the interface around them, but the service served neither field, so the UI fell back to the clean output and **there was no purchase gate at all**. `GET /v1/jobs/{job_id}/output` returned the finished, compliant, portal-ready file to anyone holding a job id, and a job id is handed to the browser by the preparation response. The candidate was being given for nothing the one thing the product sells. A watermark applied in the browser cannot fix this: to draw on the image the page must first hold the image, so the clean file would already be on the candidate's machine and the mark would protect nothing.
- **Decision**: Three parts, and all three are needed for any of them to mean anything. (1) The service renders a **watermarked, reduced-resolution copy** of every prepared file at preparation time and serves it at `GET /v1/jobs/{job_id}/preview`. The mark is burned into the pixels, tiled diagonally across the whole frame, and the copy is re-encoded from the downscaled raster, so there is no layer to strip and no original underneath. (2) A job prepared through the candidate path carries `entitlement = "preview_only"` until something releases it, and `/v1/jobs/{job_id}/output` and `/v1/kits/{kit_id}/package/download` answer **402** for such a job. (3) `preview_watermarked` is `true` only where a watermark was actually burned in, and the field is set from the artifact that was written rather than from the intent to write one.
- **Reasoning**: The reduced resolution and the mark do different jobs and neither replaces the other. Halving the long edge means the preview cannot satisfy the examination's own pixel specification, so it is not submittable even if the mark were removed; the mark means it is obviously not the product even where the output was already small enough that halving it would leave something usable. **Where the output's long edge is at or under 200 px the preview is served at the output's own size**, because below that a candidate cannot judge their own face, and the mark carries the gate alone for those few examinations — recorded here rather than left as a silent floor in the code. The gate defaults **on**, following DEC-060: `model-assets/` taught us that a fresh clone and a fresh deployment host start in exactly the state the insecure default would ship, and a gate that has to be switched on is a gate that will be off in production. `EXAM_PHOTO_PURCHASE_GATE_ENABLED=false` exists for engine quality work, where judging a matte on a watermarked half-resolution copy would be judging it on the wrong thing — the same trap HANDOFF records for the MediaPipe backend. **There is deliberately no HTTP route that releases a job.** Payment is not built, and an unauthenticated release endpoint is not a weaker gate than none, it is a worse one, because it looks like protection to everyone who reads the route list. `ApiProcessingService.release_job` is the seam the Razorpay confirmation will call from inside the process once it exists, and until it does the honest state of the product is that files are prepared and previewed but not yet deliverable. `/v1/process` is untouched and its jobs are released on creation: it serves the local-only rule-admin console, names no examination, and never reaches a candidate.
- **Consequences**: **Nothing in the candidate path can download a clean file until payment is built**, which is the true state of a product whose payment step does not exist, and is a change from silently giving it away. The test bench at `/test` shows the watermarked preview and says so; run it with the gate off to judge output quality. **A PDF deliverable gets no preview** — `preview_url` is null and `preview_watermarked` is false — because rasterising a PDF page needs a rasteriser this repository does not have (PyMuPDF is AGPL and was excluded for that reason, see `pyproject.toml`). The clean PDF is still gated, so a candidate buying a certificate scan currently buys it unseen; the fix is a preview-only rasteriser, which DEC-052 does not forbid since that rule governs the *delivered* file. A preview that cannot be rendered never fails the job: the preparation succeeds, the fields stay null, and the UI's existing fallback text is shown. `Pillow` is pinned to `>=10.1.0`, the release that added a scalable default font; without it the only built-in font is a bitmap at one size and the mark could not be scaled to the image.
- **Affected Modules**: `services/image-engine/src/exam_photo/preview/`, `api/service.py`, `api/app.py`, `api/contracts.py`, `api/jobs.py`, `api/settings.py`, `api/testbench.html`, `pyproject.toml`, `tests/preview/`, `tests/api/test_kit_endpoints.py`.
- **Approval Owner**: Product Owner

### DEC-064: A Deployable Service Warms Itself, Sweeps Itself, and Says Which Half It Is
- **Date**: 2026-09-06
- **Status**: Approved
- **Problem**: Four defects stand between the service and a public host, and each is invisible in local use. (1) **Nothing warms the model.** onnxruntime pays a one-time thread-pool and arena spin-up on its *first* inference in a process (DEC-054), so the first candidate to reach a fresh worker waits 100-150 s -- and `/health` returns `healthy` immediately regardless, so a load balancer has no way to tell a warm process from a cold one and will route to the cold one. nginx cuts at 60 s and Cloudflare at 100 s, so that first candidate does not merely wait, they get a gateway error, on every deploy and every restart. (2) **TTL cleanup only runs when somebody calls `POST /v1/cleanup-expired`.** Nothing calls it. Candidate face photographs -- sensitive personal data under the DPDP Act -- therefore accumulate on disk for the life of the host with no enforced expiry, while `expires_at` on every manifest asserts otherwise. (3) **CORS origins are hardcoded to `localhost:3000`**, so the first request from a real domain fails as an ordinary `TypeError` in the browser, indistinguishable from a dead server. (4) **There is no authentication anywhere**, and `/v1/process` is both unauthenticated and exempt from DEC-063's purchase gate, which makes it a free 10-second-of-CPU pipeline for anyone who finds it.
- **Decision**: (1) A `lifespan` hook starts a **background** warmup thread that builds the pipeline and runs one real inference, and `GET /ready` reports `warming` / `ready` / `failed` with 503 on the first and last. `GET /health` is unchanged and stays liveness-only. (2) The same hook starts a sweeper thread calling `cleanup_expired_jobs()` every `EXAM_PHOTO_CLEANUP_INTERVAL_SECONDS` (default 300). (3) `EXAM_PHOTO_ALLOWED_ORIGINS`, comma-separated, replacing the constant. (4) **An operator token gates the operator surface only** -- `/v1/process`, `/v1/rules/validate`, `/v1/cleanup-expired` and `/test` -- via `EXAM_PHOTO_OPERATOR_TOKEN`. The candidate surface stays open and is protected instead by a **global concurrency limit** on preparation (`EXAM_PHOTO_MAX_CONCURRENT_PREPARATIONS`, default 2), which returns 429 with `Retry-After` when full.
- **Reasoning**: **Warmup is a background thread rather than a blocking startup** because a process that binds late is indistinguishable from a process that crashed; one that binds immediately and answers `/ready` with `warming` plus an elapsed count is something an orchestrator can act on. Splitting readiness from liveness is what makes a rolling deploy possible at all -- without it every deploy takes the fleet cold simultaneously. The warmup runs a **real inference and not merely a model load**, because DEC-054 measured the one-time cost as falling on the first *inference*; loading the graph and calling nothing would leave the whole penalty for the first candidate and report itself ready. Where the weights are absent, warmup fails loudly and `/ready` says so naming the acquisition scripts, which is DEC-060's loud-failure-at-deployment reaching the one place a deployment actually looks. **On rate limiting: there is deliberately no per-IP limit.** Carrier-grade NAT on Indian mobile networks puts thousands of candidates behind a single address, so a per-IP quota either punishes a shared address or is set so high it protects nothing; HANDOFF already records this for session identity and the same fact governs here. What actually needs protecting is the CPU, and a global concurrency cap protects it regardless of who is calling and without ever penalising a candidate for their carrier. Real abuse filtering belongs at the edge (Cloudflare), and saying so is better than shipping an in-app half-measure that mainly hurts legitimate traffic. **On the auth split**: a token cannot protect the candidate surface, because the browser would have to carry it and would therefore hand it to anybody who opened the network tab. It can protect the operator surface, which no candidate touches, and that is where the asymmetric damage is -- `/v1/rules/validate` and the rule-admin console change what the platform believes an examination requires, and `/v1/process` is an ungated pipeline. **The token is optional and its absence is loud**: with no token set the operator routes stay open and `/ready` reports `operator_surface: "unauthenticated"`, so the state is visible on the one endpoint a deployment checks rather than silent.
- **Consequences**: The first request after a restart is served by a warm process, or refused by a load balancer that can see it is not one. Measured on this machine while building it: the **first** segmentation in a process costs **48.8 s** and the second **7.7 s**, so warmup absorbs roughly 41 s that used to fall on a candidate -- lower than the 100-150 s HANDOFF records, which was presumably measured against a cold page cache. Readiness carries **five** warmup states, not three, because `warmup_on_boot=false` must not mean a permanent 503: `not_started` (the hook has not run, and the process claims nothing), `warming`, `ready`, `failed`, and `skipped` for a host that deliberately turned warmup off, which reports ready. Collapsing `skipped` into `not_started` would make the flag unusable behind a load balancer, which was caught in review rather than in production. Separately found and closed while wiring the concurrency cap: **the document endpoint bounded each file's size and not the number of files**, so one request could hand the service an unlimited number of 5 MB uploads to hold in memory and write to disk; `max_document_files` defaults to 20. Expired artifacts are actually deleted, which is the difference between a retention policy and a retention claim. **Two things were deliberately not decided here.** `job_ttl_seconds` stayed at 3600: DEC-058 records that raising or lowering it is a privacy decision to be taken on its own evidence and not a convenience knob, and `docs/UI_ENGINE_HANDOFF.md` separately contemplated a *30-minute* deletion guarantee, half the then-current value -- the sweeper makes either number real, but which number it should be was the product owner's. **Settled by DEC-066: thirty minutes**, which also found that the sweeper alone left an expired file readable until the next sweep, so retention is no longer enforced by this timer alone. And the concurrency default of 2 is a placeholder sized to a small VPS: it should be set to roughly the core count of the deployment box, measured, not guessed. `/health` keeps its existing contract so nothing already pointing at it breaks.
- **Affected Modules**: `services/image-engine/src/exam_photo/api/app.py`, `api/service.py`, `api/settings.py`, `orchestration/rule_pipeline.py`, `tests/api/test_service_hardening.py`.
- **Approval Owner**: Product Owner

### DEC-065: The Deployment Is One Origin, and the Weights Are Not in the Image
- **Date**: 2026-09-06
- **Status**: Approved
- **Problem**: DEC-064 gave the service a readiness endpoint, a warmup, a sweeper, a configurable origin list and an operator token, and nothing to run it. There was no Dockerfile, no compose file and no reverse proxy, so `/ready` was an endpoint nothing read and the hardening settings were knobs nobody could turn. The product owner has settled the shape -- one small VPS now, a GPU box only if scale demands it -- so the question was what that VPS actually needs.
- **Decision**: `deploy/`, holding a two-target Dockerfile for the engine, a separate one for the web app, a compose file, a Caddyfile and an env template. **Model weights live in a named volume filled by a one-shot `model-fetch` service, never in an image layer.** **Caddy serves the app at `/` and proxies `/v1/*` to the engine, so the deployment has one origin and no CORS.** The engine's healthcheck calls `/ready` and the proxy waits on `service_healthy` before routing to it. `/health` and `/ready` are answered only from private address ranges.
- **Reasoning**: **The measurement that governs the whole shape is memory: a warm worker holds ~2.4 GB resident and peaks near 2.9 GB during inference.** That was measured here rather than assumed, and it means a 2 GB VPS -- the ordinary reading of "one small VPS" -- **cannot run this at all**; the floor is 4 GB for a single worker. It also corrects HANDOFF's throughput plan, which proposed "several worker processes each holding a warm pipeline" without noting that each costs 2.4 GB, so four workers is a 16 GB box and not a configuration change. **Two Dockerfile targets** because running the exported ONNX graph needs onnxruntime alone while producing it needs torch, transformers and timm; keeping ~2 GB of build-only dependencies out of the serving image is the entire point of the ONNX export (DEC-054), and baking them in would have quietly discarded that benefit. **Weights in a volume** because they are ~2.5 GB that never change between deploys, so an image layer makes every deploy a multi-gigabyte pull of identical bytes on a connection where that is the slowest part of shipping. **One origin** because the alternative is maintaining an allow-list to permit a request the browser would not otherwise have to make; CORS here is a problem created by a deployment choice, and the fix is the choice. **The probes are private** because `/ready` deliberately reports the matting backend, the purchase-gate state and whether the operator surface is authenticated -- exactly the reconnaissance an attacker wants, and the same fields that make it useful to an operator, so the answer is to restrict who may ask rather than to say less. **`EXAM_PHOTO_REPO_ROOT` is set explicitly** because `find_repo_root()` walks up from the package looking for `AGENTS.md` or `model-manifests/`, which cannot succeed once the package is installed into site-packages; the env var is the escape hatch the code already provides and no code change was needed. The web image reproduces the repository layout rather than flattening the app, because `catalogue.server.ts` resolves the catalogue as `process.cwd()/../../examples/rules` -- flattening it would make that path escape the filesystem and **every exam page would silently vanish from the build**, so the build asserts that exam pages exist rather than trusting it.
- **Consequences**: A deploy is three commands and the first candidate after one is served by a warm process. **The compose file is not zero-downtime**: `up -d --build` restarts the engine and the next request waits for warmup; the readiness endpoint makes a rolling restart possible under a real orchestrator, but compose alone will not do it. `next start` is used rather than `output: "standalone"`, which would produce a much smaller web image but requires a line in `apps/web/next.config.ts` -- the UI lane's file, and not the engine lane's to change unilaterally. **This deploys a product that cannot take money**: DEC-063's gate refuses every clean file until `release_job` is called and nothing calls it, so deploying before Razorpay serves watermarked previews and collects nothing. Left explicitly out and recorded here rather than half-built: log shipping, metrics, alerting, backups, and edge abuse filtering, which belongs at Cloudflare in front of this rather than in the application. Separately hardened while writing this: `cleanup_expired_jobs` now tolerates a racing delete, because each uvicorn worker runs its own sweeper and two of them scanning the same manifests could previously abort a sweep partway. **Amended 2026-09-06**: `deploy/.env.example` was never actually in the repository -- `.gitignore`'s `.env.*` rule matched it, so this entry and `deploy/README.md` both pointed at a template a fresh clone did not have. A `!deploy/.env.example` negation now carries it; it holds only defaults and empty placeholders, and it is the one `.env.*` file that is documentation rather than configuration.
- **Affected Modules**: `deploy/`, `.dockerignore`, `services/image-engine/src/exam_photo/api/service.py`.
- **Approval Owner**: Product Owner

### DEC-066: Thirty Minutes, Enforced at the Deadline and Not at the Next Sweep
- **Date**: 2026-09-06
- **Status**: Approved
- **Problem**: Two numbers described the same promise and disagreed. `job_ttl_seconds` defaulted to **3600** while `docs/UI_ENGINE_HANDOFF.md` listed a **30-minute** deletion guarantee as outstanding -- half of it. DEC-058 raised this and deliberately left it open, DEC-064 built the sweeper that makes either number real and again declined to pick one, and both recorded that no public deletion claim may ship until the setting and the claim agree. Settling the number then exposed the harder half, which neither entry had noticed: **expiry was enforced only by the sweeper**, which runs every `cleanup_interval_seconds` (300 by default). Nothing on the read path consulted `expires_at`. A job that passed its deadline stayed fully readable until the timer next came round, so `GET /v1/jobs/{id}/output` returned **200 and the clean file** for up to five minutes after the moment the product promises it is gone -- verified by disabling the new check and watching the test go green at 200.
- **Decision**: **Thirty minutes** (`job_ttl_seconds` defaults to 1800), and expiry is enforced on the read path as well as by the timer. `ProcessingJobRecord.is_expired()` is the single predicate; `ApiProcessingService.expire_job_if_due()` erases the artifacts and marks the record `DELETED` on the way to serving any of the six job routes; `JobRegistry.jobs_in_kit` excludes an expired job so a package assembled in the gap cannot contain one; and `cleanup_expired_jobs` uses the same predicate and remains the backstop for jobs nobody reads again. An `expires_at` that cannot be parsed reads as **expired**.
- **Reasoning**: **A retention promise measured in minutes cannot carry a five-minute hole**, and a sweep interval is a scheduling detail that must not be load-bearing for a privacy claim -- an operator raising the interval to reduce disk churn would silently lengthen the window in which deleted data is still served. Enforcing at the deadline decouples the promise from the timer entirely: the interval now decides only how promptly unread bytes leave the disk, and never how long a candidate's face photograph remains obtainable. **Marking the record `DELETED` rather than introducing an `expired` status is deliberate**: every route already refuses a deleted job and `JobStatusResponse.status` is part of the contract `apps/web/src/lib/types.ts` mirrors, so a new enum value would be a change request to the UI lane for no gain a candidate could perceive -- expired and deleted are the same fact to them. **Thirty over sixty** because the product owner chose it on the privacy side of the trade, which is the side DEC-058 said the decision had to be taken from. The cost is stated rather than hidden: a candidate who pays and does not download within thirty minutes must prepare the file again. That is real, it is the price of the shorter window, and it is why the number is the owner's and not an implementation detail. **A corrupt deadline reads as expired** because there is no safe reading of a retention deadline nobody can decode, and fail-open here would make a damaged manifest the one path to unlimited retention of a face photograph.
- **Consequences**: The 30-minute deletion guarantee in `docs/UI_ENGINE_HANDOFF.md` is now the behaviour and may be published; the checklist item in `deploy/README.md` is closed and `deploy/.env.example` carries 1800. **A candidate who leaves a prepared file for half an hour loses it** and pays nothing further, but does spend the preparation again -- once payment exists, the refund or re-preparation policy for that case is a product decision this entry does not make, and it should be made before launch rather than discovered by the first candidate it happens to. Retention is now enforced in two places rather than one, which is the point: the read path bounds *access* exactly, the sweeper bounds *disk residency* to the deadline plus at most one interval. `cleanup_interval_seconds` stays 300. Reads on the job routes now have a side effect -- erasing an expired job -- which is ordinary lazy expiry but is recorded here because a `GET` that deletes is worth knowing about before reading the routes. **This closes open risk 6 in HANDOFF.md.**
- **Affected Modules**: `services/image-engine/src/exam_photo/api/settings.py`, `api/jobs.py`, `api/service.py`, `api/app.py`, `tests/api/test_retention_window.py`, `deploy/.env.example`, `deploy/README.md`, `docs/UI_ENGINE_HANDOFF.md`.
- **Approval Owner**: Product Owner

### DEC-067: The Deadline Is Announced Before It Arrives, and a Candidate May Postpone It Once
- **Date**: 2026-09-06
- **Status**: Approved
- **Problem**: DEC-066 set retention at thirty minutes and left one question open: a candidate who pays and returns after thirty minutes has bought a file that no longer exists. The product owner ruled: **warn before checkout, and offer to keep the file alive longer.** The two were offered as alternatives and are not. An extension can only be taken *before* the deadline -- after it the artifacts are gone and there is nothing to extend -- so a candidate who was never told the deadline exists will never use the extension. **The warning is a precondition of the extension being usable at all**, not a substitute for it.
- **Decision**: (1) The warning is the interface's, and the engine already served what it needs: `expires_at` is on `JobStatusResponse` and `PrepareRequirementResponse`, it is authoritative since DEC-066, and it was already declared in `apps/web/src/lib/types.ts`. No engine change was required and none was made. (2) `POST /v1/jobs/{job_id}/extend` grants one more full retention window to a **live** job, bounded by `job_max_lifetime_seconds` measured from the job's creation. It answers 404 for an expired or unknown job, 409 for a job at its ceiling, and returns the new `expires_at` with an `extendable` flag. That flag is also added to `JobStatusResponse`, additively.
- **Reasoning**: **The ceiling is 3600 seconds, and the number is an argument rather than a preference.** 3600 was the unconditional TTL before DEC-066, so the longest a file can now live -- and only because the candidate asked for it -- is exactly what every file used to get without asking. The extension option therefore cannot make the platform hold anything longer than it already did, and the ordinary case is half of it. That framing is what makes an unauthenticated route defensible: the worst an attacker holding a job id can achieve is the retention the product shipped with last week, and they would already have the file. **A new window is measured from now rather than added to what remains**, because a candidate asking with two minutes left wants thirty minutes, not thirty-two; and because measuring from now, combined with a ceiling measured from creation, means repeating the request cannot walk a file forward indefinitely. **A job at its ceiling is refused with 409 rather than given a 200 whose deadline did not move**, because a success that changes nothing is the failure mode that teaches a candidate to trust a button that has stopped working. **Extension does not release.** Retention and payment are separate gates and a route that quietly did both would be DEC-063's release endpoint under another name; a test pins that an extended job still answers 402. **A `created_at` that cannot be parsed grants no extension**, matching DEC-066's treatment of an unparseable `expires_at`: a job whose age is unknowable has no demonstrable room left, and every unreadable timestamp resolves against retention.
- **Consequences**: The published claim becomes *"deleted within thirty minutes, or within an hour if you ask us to keep it"* rather than a flat thirty. **That is a weaker promise than DEC-066's and it must be published accurately** -- writing "deleted in 30 minutes" beside a button that extends to 60 is the exact mismatch DEC-066 existed to close, and it would be worse for having been introduced knowingly. **The interface half is outstanding and the feature is inert without it**: nothing warns a candidate that the deadline is approaching, so nothing prompts the extension, so in practice today a candidate still discovers expiry as a 404. `extendable` on `JobStatusResponse` and the `/extend` route are declared in the engine and are the UI lane's to adopt; `types.ts` is theirs to change. Unauthenticated, in line with the rest of the candidate surface, and bounded as argued above rather than by a secret a browser could not hold anyway. Not decided here and worth deciding before launch: whether the extension is offered to everyone or only after payment, which is a pricing question rather than a privacy one.

### DEC-069: The Webhook Is the Caller DEC-063 Left Room For, and It Cannot Yet Check the Price
- **Date**: 2026-09-07
- **Status**: Approved
- **Problem**: DEC-063 built the purchase gate and deliberately left `ApiProcessingService.release_job` with nothing calling it, recording why: *"an unauthenticated release endpoint is not a weaker gate than none, it is a worse one, because it looks like protection to everyone who reads the route list."* Every prepared file therefore answered 402 and the product could not take money. The missing piece was never the release itself but a caller whose authority could be proved.
- **Decision**: `POST /v1/payments/razorpay/webhook`. The shared-secret HMAC-SHA256 signature is verified **over the raw request body, before the payload is parsed at all**, and only `payment.captured` and `order.paid` release anything. The order's or payment's `notes` name a `job_id` or a `kit_id`; a kit releases every live job in it. Verification and payload reading live in `api/payments.py` as pure functions that touch no service, no registry and no disk. The payment id, amount and currency are written onto the manifest as a reconciliation trail. `GET /ready` reports `payments: configured | not_configured`.
- **Reasoning**: **The signature is the entire difference between this route and the one DEC-063 refused to write**, so it is checked first and over the bytes as received -- re-serialising the JSON would change whitespace and key order and the digest would never match again. **An authorised payment must not release a file**: an authorisation is a hold that can still fail, and only capture means the money moved. **An event this service does not act on is acknowledged with 200, not refused**, because Razorpay retries anything it is not told arrived and a 4xx turns one ignored refund into an indefinite retry loop. **Idempotency is structural rather than bolted on** -- releasing an already-released job sets the same entitlement again -- which matters because retries guarantee some payments arrive twice. **A rejection says only "Webhook rejected"**: a forger must not be able to bisect their way to a valid request by reading which check failed, so the reason goes to the operator's log and nothing else. **An unconfigured secret refuses everything** rather than accepting, following DEC-060: a host that has not set it is in exactly the state an insecure default would ship. **An unknown job in a bundle does not abort the rest**, because the money has already moved and one bad identifier must not cost a candidate their other files. **An expired job cannot be released** (DEC-066): its artifacts are gone, so an entitlement to it would be a manifest claiming a right to nothing.
- **Consequences**: **The product can take money, and must not yet be pointed at a live Razorpay account.** The webhook proves Razorpay sent the event; it cannot prove the candidate paid the asking price, because nothing in the engine knows what was owed. `amount` is recorded and not checked. The missing companion is **server-side order creation** -- an order the service itself creates at a price it computes, so that Razorpay's own guarantee that a payment matches its order becomes a guarantee about our price. Until then an order created with arbitrary `notes` and a nominal amount would release files, and this is recorded here rather than left for someone to find. Also outstanding and named in `docs/UI_ENGINE_HANDOFF.md`: the UI must put `job_id` or `kit_id` into the order's notes, or a verified payment releases nothing and the candidate pays for a file they never receive -- the webhook logs that case loudly and answers `no_targets`. The route is deliberately **not** behind the operator token: Razorpay cannot send one, and a shared-secret signature over the body is a stronger proof of origin than a bearer token. Refund handling is not built; DEC-067's question about a candidate whose paid file expires is still the product owner's.
- **Affected Modules**: `services/image-engine/src/exam_photo/api/payments.py`, `api/app.py`, `api/service.py`, `api/jobs.py`, `api/settings.py`, `tests/api/test_razorpay_webhook.py`, `deploy/.env.example`, `deploy/README.md`.
- **Approval Owner**: Product Owner

### DEC-070: The Price Is Computed Where the Candidate Cannot Reach It
- **Date**: 2026-09-07
- **Status**: Approved
- **Problem**: DEC-069 built a webhook that verifies Razorpay's signature and releases the files an order names, and recorded that it must not be pointed at live keys: it proves Razorpay sent the event but not that the candidate paid the asking price, because nothing in the engine knew the prices. A browser-created order would have let anyone pay a rupee for a bundle. The product owner has now settled pricing, which is the input that was missing: **Rs 3 for any single deliverable that is an image and needs the model to work on it; Rs 5 for two; Rs 8 for three or more. Document work -- image to PDF, compression, rearranging, merging -- is free.**
- **Decision**: `GET /v1/kits/{kit_id}/quote` prices a kit from the jobs on disk and itemises why each deliverable is charged or not. `POST /v1/kits/{kit_id}/order` creates a Razorpay order **server-side at that amount**, carrying `kit_id` in its notes, and returns the order id and publishable key for Checkout. Pricing is a pure module (`api/pricing.py`); order creation is behind an `OrderGateway` protocol with an HTTP implementation, an unconfigured one that refuses, and a fake for tests. Amounts are paise throughout, so no float touches a price.
- **Reasoning**: **The route accepts no amount at all**, rather than accepting one and validating it. A validated amount is still an amount the caller chose, and every validation is a place the check can be wrong; a route with no such parameter cannot be argued into charging less. That is the property the tests pin first. **Razorpay's own guarantee does the rest**: it guarantees a payment matches its order, so once the order is ours at a price we computed, a verified `order.paid` is proof of our figure -- which is exactly what DEC-069 lacked. **Charging is decided by requirement type, not by what the pipeline happened to produce**, because the owner's rule is about the kind of work: an image the model works on is charged, a document assembled into a PDF is not. A handwritten declaration is charged because it goes through the ink pipeline exactly as a signature does; a certificate scan is not, because its work is assembling a PDF and candidates get that free elsewhere. **The top tier is a ceiling rather than a step**: three deliverables and six both cost Rs 8, which makes "everything an examination asks for, for eight rupees" a promise the code keeps rather than a slogan. **An already-released job is excluded from the quote**, because charging twice for a file the candidate can already download is very hard to argue was accidental. **A quote is itemised with a reason per line**, so a candidate can be told *why* their certificates cost nothing, and so an argument about a charge is settleable afterwards. **A gateway failure is 503 with no Razorpay text in it**: a payment provider's error string is not something to render into a page. **A host with no credentials gets a gateway that refuses**, following DEC-060 -- the alternative is a deployment that silently falls back to something.
- **Consequences**: **The webhook can now go live**, because the amount is bound to the order and the order is ours. The remaining gap is not in this path: `httpx` is now a declared runtime dependency rather than one inherited transitively from the test client, which it always was in a serving image that installs no test extras. **Prices live in code, not in the environment.** A price is a product decision and a deployment must not be able to change one silently; altering the ladder is a code change with an entry here, which is the intended friction. **Nothing reconciles a payment against its quote after the fact.** If a candidate prepares a third file between quoting and paying, the webhook releases all three for the two-file price -- accepted deliberately as the cheaper error, since the alternative is refusing a file the candidate has already paid something for. The reverse case, paying for more than is released, cannot happen: releases are per-job and idempotent. **Refunds are still not built**, and DEC-067's question about a paid file that expires is still open. `GET /ready` reports whether payments are configured, but deliberately never the keys or the prices.

### DEC-071: The Order Is the Purchase, Not the Kit
- **Date**: 2026-09-07
- **Status**: Approved
- **Problem**: DEC-070 computed the price from the jobs on disk and created the order at that amount, then told the webhook to release **the kit** -- everything in it when the payment arrived. Those are not the same set. A file prepared between the order and the payment would have been released against a price quoted before it existed, and DEC-070 recorded that as an accepted error. The product owner rejected the premise: payment follows a review of exactly what the candidate has chosen to buy, so the release must be exactly that and nothing else. They are right, and the fix is not to rely on the interface making it unlikely.
- **Decision**: An order records **the exact job ids it was priced from**, in an `OrderRegistry` stored under `_orders/` beside the artifacts. A verified payment resolves its `order_id` to that record and releases those jobs and no others. Where the order is not one we created -- an operator raising one by hand in the Razorpay dashboard -- the webhook falls back to the identifiers in the notes, as before. `mark_paid` records the settlement, idempotently.
- **Reasoning**: **The defect was describing a purchase by a container that can change.** A kit is a working set a candidate adds to; an order is a fixed thing that was priced. Once the order names its jobs there is no window to reason about, no timing to get right and no race to lose -- a file prepared afterwards is simply not in the order. That is a structural fix rather than a narrower one, which is why it is preferred to shortening the window or locking the kit during checkout. **Every live job is recorded, not only the charged ones**, because document work is free *with* a purchase: a certificate is gated like everything else and is delivered by the same payment, so an order that carried only the chargeable jobs would take money and withhold the free files. **Orders live outside the job directories** because they outlive them: retention erases a candidate's photograph after thirty minutes (DEC-066), and the record that they paid must not go with it -- it is the only evidence available if they later say they were charged and received nothing. **The order id is validated against a pattern before it becomes a filename**, because it arrives inside a payload from the network. **Failing to record an order fails the request**, even though the order already exists at Razorpay: paying against an order we cannot resolve would release nothing and keep the money, which is worse than a candidate retrying.
- **Consequences**: The quote and the release are the same set by construction. A file prepared during checkout stays gated and is priced on its own in the next quote -- verified by test, along with the reverse: with the order lookup disabled the late file is released and three files go out for a two-file price. **The order record is also the trail a refund needs**: what was ordered, for how much, when, which payment settled it, and which jobs it covered, all surviving the deletion of the files themselves. What it does not yet record is **delivery** -- whether the candidate actually downloaded or received the file -- which is the other half of deciding a refund claim and is not built. `_orders/` is never swept: the artifacts it refers to expire, the record does not, and nothing yet ages it out. That is deliberate for now and will need a retention decision of its own once real orders accumulate, on the same evidence footing as DEC-066.

### DEC-072: Delivery, and the Evidence a Refund Is Decided On
- **Date**: 2026-09-07
- **Status**: Approved
- **Problem**: A candidate who paid could only download, and only inside the thirty minutes DEC-066 enforces. Nothing carried the file past that window, which is the one failure the product owner named specifically: *"then no issues of them not getting the deliverables even after paying."* Separately, their refund rule -- **paid, and not delivered** -- was undecidable, because nothing recorded what actually reached the candidate. The two are the same problem seen from either end.
- **Decision**: `POST /v1/kits/{kit_id}/email` attaches the kit's **released** files and sends them over SMTP. Every download and every send attempt is recorded on the job, and the first delivery of anything an order covers is recorded on the order. `GET /v1/orders/{order_id}/evidence` is operator-gated and answers what a refund needs. A `wa.me` link needs nothing from the engine: WhatsApp carries the text and the candidate carries the file.
- **Reasoning**: **The candidate's email address is used and not stored.** It is personal data under the DPDP Act with no purpose once the message is sent, so what is kept is a masked form -- `c***@example.com` -- which settles "you sent it to the wrong address" and is useless for anything else. A test asserts the unmasked address never reaches the manifest, because this is the kind of property that decays silently. **Only released files are attached.** Emailing a preview would put a watermarked half-resolution copy in an inbox looking like the thing that was bought; emailing a clean file before payment would be the purchase gate with a hole in it. **Evidence lives at two levels on purpose.** Per-job detail is rich and dies with the job at thirty minutes; the order-level `delivered_at` and `delivery_method` survive, because a claim arrives *after* the file is gone and that is exactly when the evidence is needed. The order record therefore carries no address at all -- it outlives the retention window, and keeping a candidate's email that long serves nothing. **A failed send is recorded as a failure**, with the error, so a claim following a bounce finds the bounce rather than silence. **The evidence endpoint establishes our facts and not the candidate's honesty.** A file can be delivered and still not arrive -- wrong address, spam folder, an interrupted download -- so it answers "was this paid" and "did anything leave", and the decision stays a person's. A host with no SMTP configured gets a sender that refuses, following DEC-060: telling a candidate their file is on the way and sending nothing is worse than being plainly switched off.
- **Consequences**: A candidate can leave with their files by download or email, and the thirty-minute window stops being a way to lose something already paid for. The email states the deletion time and says to keep the message, so the attachment becomes the durable copy. **Attachments are capped at 15 MB total** and a kit exceeding it is refused rather than truncated. Recording a download makes `GET /output` a route with a side effect, which is worth knowing before reading it. `mark_delivered` scans the orders directory to find the order covering a job, which is fine at present volume and is the first thing to index if `_orders/` grows large -- it is already flagged as needing a retention decision of its own (DEC-071). **Refund *processing* is still not built**: this decides a claim, it does not issue money, and Razorpay refunds are a separate integration. The product owner's rule -- refund only where payment arrived and delivery did not, reviewed case by case -- is now answerable.

### DEC-073: The Threat Is Capacity, Not Cost, and the Limit Is Set on Evidence
- **Date**: 2026-09-07
- **Status**: Approved
- **Problem**: Preparation is free until the candidate decides to buy, and it is the expensive thing this service does -- roughly ten seconds of CPU and 2.4 GB resident per photograph (DEC-054, DEC-065). Somebody could run hundreds of images through it and never pay. The product owner asked what to do about it.
- **Decision**: Three things, and the first is the finding rather than a control. **The money at risk is negligible**: at one worker on a 6 GB VPS the marginal compute is on the order of a hundredth of a rupee per photograph, so a hundred free preparations cost about one rupee of a machine already paid for. **What is actually at risk is availability** -- a script saturating the queue on a deadline day, when every refused candidate is a lost sale. So: (1) **Cloudflare Turnstile**, verified server-side, on the prepare route, because automated abuse is the only kind with the volume to matter; (2) **a per-kit free-preparation allowance**, off by default, which a purchase clears; (3) **per-kit counters and an operator-gated `GET /v1/metrics/usage`** reporting preparations, conversion and the distribution.
- **Reasoning**: **Nothing here is per-IP.** Carrier-grade NAT puts thousands of Indian mobile candidates behind one address, so a per-IP quota either punishes a shared address or is set so high it protects nothing -- DEC-064 established this for rate limiting and the same fact governs here. **The allowance is a speed bump, not a security control**, and is documented as such: it is bypassed by clearing browser storage, because `kit_id` is minted by the browser. Pretending otherwise would be the mistake; it exists to add friction to idle re-uploading, and the thing that actually stops a script is the challenge. **A purchase clears the allowance** because the limit exists to bound *free* use, and stopping a paying candidate mid-kit would be the worst possible false positive. **The allowance defaults to off**, which is the substance of the decision: the counters exist to answer how many preparations a real candidate makes, and a limit set before that evidence is a guess whose failure mode -- set too low -- costs sales silently. **The summary reports a distribution, not a mean**, because the mean of a population containing one script and a thousand candidates describes neither. **The challenge fails open where the payment secrets fail shut**, and the asymmetry is deliberate: an unverified webhook releases files nobody paid for, while an unchallenged preparation costs a fraction of a rupee, so refusing every candidate because Cloudflare is unreachable is the more expensive error. Turnstile is verified *before* the upload is read, so a request that is going to be refused does not first cost the bytes.
- **Consequences**: A 403 is possible on preparation where a challenge is configured and fails, and a 429 where an allowance is configured and spent -- both with candidate-safe messages, and the 429 says buying lets them carry on. **Counters live in `_usage/`, outside the job directories**, because they must survive retention: a counter erased with the jobs every thirty minutes would reset the allowance twice an hour, which is the same as having none. That directory grows without bound and is never swept, the same open question `_orders/` carries (DEC-071); both want one retention decision rather than two. **The interface must send `cf_turnstile_response`** with the preparation once a site key is configured, or every preparation is refused -- recorded in `docs/UI_ENGINE_HANDOFF.md`. Deliberately not built: any attempt to identify a repeat candidate across kits, which would mean the fingerprinting this product has avoided for the same DPDP reasons it avoids IP identity.
- **Affected Modules**: `services/image-engine/src/exam_photo/api/protection.py`, `api/app.py`, `api/service.py`, `api/settings.py`, `tests/api/test_protection.py`.
- **Approval Owner**: Product Owner

### DEC-075: Progress Comes From the Work, Not From a Timer
- **Date**: 2026-09-07
- **Status**: Approved
- **Problem**: Preparation blocks for about ten seconds and returns the finished job, so the interface had nothing to show but a spinner. The design brief asks for a ring that fills while the photograph is made. The only way to build that against a blocking call is to invent the number, and an invented one sits at 90% while nothing happens the first time the network is slow -- exactly the detail that makes a premium interface feel fake.
- **Decision**: The client mints a `progress_token`, sends it as a form field with the upload, and polls `GET /v1/progress/{token}` alongside the still-blocking preparation. The pipeline calls a `progress_callback` from `record_stage`, which every stage already passes through. Progress is stored on disk under `_progress/`, weighted by measured stage cost, and swept on the existing artifact timer.
- **Reasoning**: **The job id cannot identify work in flight**, because it is only known once the work finishes -- which is why the token is the caller's to mint. That keeps `prepare` synchronous and its contract unchanged; the better long-term shape is 202-plus-polling (DEC-055) and it is a breaking change, so it stays open rather than being smuggled in here. **On disk rather than in memory** because a deployment runs several uvicorn workers and the poll will not reliably land on the one doing the work; an in-memory dictionary would answer "unknown" at random, which is worse than no bar at all. **The weights are measured shares of a real run**, so the bar moves at roughly the rate the work happens -- the two BiRefNet inferences are about eight of the ten seconds and carry 64% of the weight between them, without which the bar would stall for most of the wait. They are honest about *what* is happening even where they are wrong about when it will end. **It never reaches 1.0 until the work is done**, so it cannot sit full while a candidate waits, and **it never goes backwards**, because a retreating bar reads as a fault even when the work is fine. **An unknown token is 404, not a zeroed state**: "never heard of this" and "not started yet" are different answers and a client that cannot tell them apart waits forever on a typo. **Every failure path is swallowed.** Progress is a courtesy to the interface and must never be the reason a photograph is not made; the callback is wrapped, the writes are wrapped, and a malformed token is ignored rather than raised on.
- **Consequences**: The interface can show real stage names and a real fraction. `_progress/` is swept on the DEC-064 timer, so unlike `_orders/` and `_usage/` it needs no retention decision -- progress is genuinely ephemeral. The stage labels are candidate-facing English rather than the internal names, because "foreground decontamination" is precise and means nothing to anybody. Polling adds a second concurrent request per preparation, which is cheap: reading one small file. **The weights will drift** as the engine changes and nothing detects that automatically; they are a presentation detail and being slightly wrong costs nothing, but they should be re-measured whenever stage costs move materially.
- **Affected Modules**: `services/image-engine/src/exam_photo/api/progress.py`, `api/app.py`, `api/service.py`, `orchestration/rule_pipeline.py`, `tests/api/test_progress.py`.
- **Approval Owner**: Product Owner

### DEC-076: Both Lighting Variants Are Made Once, So Switching Is Instant
- **Date**: 2026-09-07
- **Status**: Approved
- **Problem**: DEC-074 gave the candidate control over the lighting correction, and the control cost ten seconds to exercise: the correction happens inside the pipeline, so toggling meant preparing again. The product owner asked for it to be instant. Preparing twice is not the answer -- it doubles the expensive work and, with DEC-073's allowance, would spend two of a candidate's free preparations to answer one question.
- **Decision**: When the correction actually changes something, the pipeline composes and compresses **both** variants in the single pass, and `POST /v1/jobs/{job_id}/enhancement` switches between them by **exchanging the two files' contents**. `enhancement_switchable` on the responses says whether there is anything to switch to.
- **Reasoning**: **Almost all the cost is upstream of the difference.** Segmentation and the crop-region re-matte are two BiRefNet inferences and about eight of the ten seconds; the variants diverge only at the foreground's tone, after all of it. So the second variant costs one `premultiply_crop_resize_composite` and one compression search -- numpy and a quality loop, no model -- against ten seconds for a second preparation. **Nothing is produced where nothing would differ.** A photograph the planner leaves alone has one variant, not two identical ones, and `enhancement_switchable` is false so the interface does not offer a control that would do nothing. **The alternate is compressed under the same ceiling and dropped if it will not fit**, so it is a compliant file in its own right rather than a preview of one -- a variant that failed the size limit is simply not offered. **The contents are exchanged, not the filenames.** This was a defect in the first implementation and is the reason it is written down: swapping which file the record points at would have delivered `..__alt.jpg`, and several portals reject an upload on its name alone. The delivered file keeps the name `generate_safe_filename` gave it, always. **The swap writes both files before touching the record**, so a failure leaves the job exactly as it was rather than naming a state that is not on disk.
- **Consequences**: Toggling is a file swap and a re-rendered preview -- tens of milliseconds against ten seconds -- and it is available before payment, which is the ordering DEC-063 depends on: the candidate decides against the real result and buys what they chose. **Preparation costs slightly more where a correction applies**: one extra composite and compression search, on the order of a tenth of the total, and one more small file on disk for the retention window. Where no correction applies there is no extra cost at all. DEC-074's note that toggling costs a re-preparation, and its warning about the interaction with DEC-073's allowance, are both superseded. The alternate is stored as `{stem}__alt.{ext}`; that name is never served and exists only to tell the two apart while both are on disk.
- **Affected Modules**: `services/image-engine/src/exam_photo/orchestration/rule_pipeline.py`, `api/service.py`, `api/app.py`, `api/contracts.py`, `api/jobs.py`, `tests/api/test_intelligent_lighting.py`.
- **Approval Owner**: Product Owner

The trustworthy part is the entire requirement and it rules out the obvious implementation. A fact somebody wrote is a fact somebody can get wrong, and one wrong fact about an examination a candidate knows well destroys the trust the whole feature exists to build. The other six — merging, reordering, rotating, compressing, naming — run inside the preparation of a file and cannot be started from the PDF page at all. A grid giving each its own screen would have offered six screens with nothing on them to do.
- **Decision**: (1) **The converter is the one row that opens a screen**, at `/pdf/to-image`, with the file picker first and the format and resolution folded under it at 150 dpi JPEG. (2) **The other six are listed under "Free with any file we prepare"**, and each row opens a sheet saying what the work does and how to get it, ending on "Find your examination". (3) **Support and the three policies keep their text and gain a search**: support filters its existing answers in place, and a policy on a phone is its sections collapsed to their headings, opened by a search that matches them. (4) Each page gets one action in the bottom bar: convert a page, write to us, ask us.
- **Reasoning**: **A row that looks like a tool and is not one is the product's worst failure mode in a small form**: DEC-056 keeps an upload control off any requirement the platform does not prepare, and the same rule governs a screen. **The converter is a route rather than a sheet** so the back button returns to the list and a refresh stays on the tool; it is `noindex` with `/pdf` as canonical because the same converter already ranks there. **The converter keeps one component with an option** (`pickerFirst`) rather than a second copy, so the failure handling and page-by-page retry built for it cannot drift between layouts; its default markup is unchanged, and a test pins the desktop order. **The support search filters the answers where they are** rather than taking a copy of their text, so it can never describe a question differently from the page and adds no wrapper to the desktop markup. **The policy sections are the same `sections` array the desktop renders**, passed to a phone component, never rewritten.
- **Consequences**: The desktop markup of `/pdf`, `/support`, `/privacy`, `/terms` and `/refund-policy` is unchanged apart from React's generated ids. At 360, 390 and 430px none of the pages overflows, every tap target is 44px or more, and no field is under 16px. **Not done, and not ours to do**: the policy pages still carry no business address and no named grievance officer, both owed by the owner before Razorpay onboarding.
- **Affected Modules**: `apps/web/src/components/m/pdf-home.tsx`, `m/pdf-tool.tsx`, `m/answer-search.tsx`, `m/policy-phone.tsx`, `components/exam/pdf-to-image.tsx`, `components/policy-page.tsx`, `app/pdf/page.tsx`, `app/pdf/to-image/page.tsx`, `app/support/page.tsx`, `lib/pdf-work.ts`, `app/mobile.css`, `app/policy.css`, `app/request.css`, `src/tests/phone-phase3.test.tsx`.

### DEC-084: The Site Asks to Be Installed Once, After It Has Been Useful
- **Date**: 2026-09-13
- **Status**: Approved (the owner asked for the install prompt in `MOBILE_PLAN.md`, and did not object to the timing recommended on 2026-09-13)
- **Problem**: The site was installable — a manifest, icons, a standalone display — but nothing invited a candidate to install it, and a browser left to itself asks on arrival, before the candidate has seen the product do anything. A candidate returns several times per examination (prepare, pay, download) and again for the next one, which is exactly the visitor a home-screen icon serves.
- **Decision**: (1) **Never on arrival.** The browser's own install bar is suppressed from a listener in the document head, which holds the event for later; it has to be in the head because the event can fire before the page's JavaScript loads. (2) **Once, after a useful moment**: a file coming back `prepared` or `prepared_with_findings`, the delivered screen, or a PDF converted — never a refused or unproduced file. (3) **A card, not a dialog**, rising from the foot of the screen above any bottom bar, on a phone only. (4) **"Not now" holds for thirty days; installing holds for good**; nothing is offered once the site is opened from the home screen. (5) **An iPhone is told the two steps** — Share, then Add to Home Screen — because Safari offers no install event, and is never shown a button that cannot work. (6) **The phone menu offers "Install the app" at any time** where installing can work. (7) **No service worker.**
- **Reasoning**: **Asking after value, not before**, because an install request with nothing behind it is dismissed, and a dismissed browser prompt may not return. **No service worker, deliberately**: this version of Next.js documents installability as a manifest plus HTTPS, and Chrome reports the site installable without one (`Page.getInstallabilityErrors` returns none). A service worker that caches pages is the easiest way to serve a candidate yesterday's rules, and this product's whole value is that the rules are current. **No claim of offline use**: the card says the app still needs the internet, because it does. **Refusals are not moments**, because an invitation arriving on top of "we could not prepare this" reads as indifference.
- **Consequences**: Verified in a real browser with mobile emulation: the head listener holds a real `beforeinstallprompt` event and suppresses the browser's own bar; no card before a moment; after one, the card sits clear of the bottom bar with 44px-plus buttons and no overflow; "Not now" is stored and a second moment shows nothing; an emulated iPhone gets the steps and a single "Got it". **Not verified, and not verifiable here**: the install dialog itself and the installed app's window, which need a real phone. Suppressing the browser's own bar means a candidate who never reaches a useful moment is never prompted — the menu item is the way in for them.
- **Affected Modules**: `apps/web/src/lib/install.ts`, `components/m/install-card.tsx`, `components/m/phone-bar.tsx`, `components/exam/use-kit.ts`, `exam/kit-success.tsx`, `exam/pdf-to-image.tsx`, `app/layout.tsx`, `app/mobile.css`, `src/tests/install-prompt.test.tsx`, `scripts/phone-check.mjs`.
- **Approval Owner**: Product Owner
